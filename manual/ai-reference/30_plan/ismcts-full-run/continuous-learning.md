# LLMから独立した継続学習

2026-10-06本人承認（信頼度A: 本チャットの明示指示）。学習・評価・モデル更新は
資源条件が許す限り24時間自律反復し、LLMは当初120分ごとに成果・異常・修正事項を確認する。
周期は学習の開始間隔・実行時間・モデル更新期限ではない。本書は採用済み仕様であり未実装部分を含む。

## 責任と実行主体

- 資源runner: [resources.md](resources.md)の共有予算・数秒単位の負荷制御・所有processを管理。
- 学習runner: 検証済みコードで生成→学習→評価→昇格→配備を実行。LLM応答・承認・利用枠に依存しない。
- supervisor: 当初120分ごとに差分報告をLLMへ渡し、停滞診断・未知障害・必要なコード修正を担当。
- 機械監視: deadline・crash・配備不整合を即時に扱う。LLMの次回起動を待たない。
- 本人: 資源上限・費用・学習対象・評価基準など方針の変更を決める。

既存controller・予算ledger・harnessを拡張し、別の成功台帳を作らない。
学習runnerはLLM workerの子の生存やsupervisor lockに依存させず、OS管理の再開可能な
単一所有processとして登録する。全計算は既存共有予算の単一ジョブ枠を取得し、並列に枠を増やさない。
LLM用の追加cron/heartbeatは作らず、既存supervisorを120分へ移す。
本人の明示停止は永続化して再登録でも維持。LLMの自然終了・利用制限と学習の手動停止を区別する。

## 状態とモデル

永続状態は `waiting_resource → generating → training → evaluating → promoting → serving_check`。
各工程から `deferred_budget / deferred_load / repair_required` へ移り、保存位置から再開する。
各jobにID・所有者・親checkpoint・engine/card/schema/config/deck/data/seed hash・開始終了・使用量を結合する。
異常を成功にせず、中断済み評価を再開して同じ試行を二重計上しない。

| モデル | 更新と使用 |
|---|---|
| learner | 重み・body・optimizer・RNG・データ位置を保存して学習を続ける |
| candidate | learnerから凍結したimmutable版。評価中に上書きしない |
| champion | 評価と配備確認を通った本番版。旧正常版と簡易AIを保持 |

対戦開始時に版を固定する。通常の昇格は新規対戦から適用し、進行中の対戦を差し替えない。
障害時の降格だけは[一人バトルの復帰契約](solo-fallback.md)に従い、未適用decision境界で行う。
候補不合格でもchampionを維持し、learnerの学習は予算内で継続できる。
engine/card/schema更新時は互換性と評価証跡を再判定し、異なる条件のデータを黙って混ぜない。

## 評価・自動昇格

1. 新しい有効データ・更新数がconfigの提出条件を満たしたときcandidateを凍結する。
   条件はI6bで校正し版管理する。評価中は候補1つ、未完了候補を次候補で上書きしない。
2. 正しさ・秘密情報境界・有限値・全入力のsmokeを通す。破損候補を隔離して原因を残す。
3. [evidence.md](evidence.md)の400戦・席交換・同一思考予算で現championと比較する。
   固定基準AI・過去モデルとの退行も別に測り、重大な退行時は昇格させない。
4. 正しさ・自然終局・強さ・速度・資源・版一致の全gateが成立した候補だけ昇格する。
   loss低下・学習回数増加・LLMの評価文を昇格証跡にしない。
5. 配備先へimmutable artifactを置き、hash/load/推論probe後に本番参照をatomicに切替える。
   切替途中のクラッシュ・二重要求を再開可能にし、失敗時は旧正常版へ戻す。

学習seedと評価seedは分離。評価は開始前にmanifestを凍結し、全試行と未終局を保存する。
同じ失敗候補をseedだけ変えて合格するまで再提出しない。再開は同じcandidate/manifestを使う。
I6bの実装時に、候補提出頻度・評価用seed更新・反復評価の誤採用制御・退行判定閾値を
評価policyとして固定し、反証テストとともにレビューする。未定義なら自動昇格不可。
現行の55%・95% CI下限50%超などの採用基準を緩和しない。
候補を増やせば偶然通る運用を防ぎ、選別に使った結果を独立な最終評価として再利用しない。

## 予算と成果報告

本人の追加指示により、定常運用の目標は可能なら24時間のAI強化とする。
旧「背景3時間/日」「改善学習20分/日」は定常運用の停止条件にしない。
瞬間的なCPU/RAM/GPU上限・他作業優先・出力量の上限を維持し、時間予算の移行は
[resources.md](resources.md)に従う。I0の校正・所有process制御未達のまま大量実行は開始しない。
対戦生成・学習・評価・復旧確認で同じ枠を共有する。評価待ちがある場合は必要な評価chunkを
先に予約し、学習が全枠を消費して評価が永久待機にならないようにする。
1chunk20分以内でcheckpointを残して連続再開する。負荷の回復後はLLMの次回tickを待たない。
400戦評価は数日にまたがってよく、2時間で完了・昇格させるために縮小しない。

120分報告は生成対戦数、有効sample数、実更新数、loss/有限値、自然終局率、候補/本番hash、
評価attempted/completed/failed/deferred、勝率/CI、先後/対面別結果、速度、資源使用と待機理由を含む。
生成対戦・自然終局・有効sample・実更新・trainingStep増分・checkpoint入出力hash・評価局数を別々に永続化する。
更新0や有効data不足をtrained/progressへ変換しない。shadow学習はdebug経路として本番runnerと区別する。
「実行中」と「学習更新あり」と「性能改善あり」を別項目にし、更新0・評価停滞・同一障害反復を検出する。
LLMは根拠ログと差分を読み、既存gate/verifierを通して必要な修正を行う。
通常の重み更新ごとにLLMレビューやGit commitを要求しない。実行コード・評価policy変更は従来の検証経路を使う。

## LLM不要運用の実証

I7の `autonomy-soak` はLLMを依存先から切り離した状態で72時間の実機観測を行う。
観測時間は計算時間ではなく、日次予算と20分chunkを守る。OS再起動を勝手に行わない。
この間の実更新・評価進捗、日次予算持越し、負荷待ちからの再開、process中断復旧を証明する。
時間経過・待機だけの72時間は合格にしない。実機負荷で未達ならpartialを保持する。
棄却・昇格・復帰の状態遷移は障害注入で反証し、本番昇格は実評価合格した候補で別途記録する。
改善候補がないことを理由に閾値を下げず、自律運用成立と強さ・実昇格の達成状況を分ける。

当初は120分ごとにLLMが確認する。自律運用証跡と機械的な停滞検出が揃った後は、親controllerが
正常tickのLLM呼出しを省略できる。学習runner・機械監視・報告保存は継続し、未知障害・
意味ある変化・修正が必要な場合にLLMを呼ぶ。LLM不通でも正常な学習・評価・昇格を継続する。
