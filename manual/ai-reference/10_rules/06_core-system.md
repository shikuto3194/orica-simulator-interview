# Core System

## 目的

コアは、バトルスピリッツのコスト支払い、ライフ、消滅判定、各種ギミックにまたがる最重要リソースです。
この章では、通常コアとソウルコアを「カード本体とは別の資源」として扱う前提を整理します。系統ごとの共有枠と配置先上限は [06a コア配置](06a_core-placement-groups.md) を参照。

## 基本整理

- コアには
  - 通常コア
  - ソウルコア
  がある。
- 基本ルールの準備では
  - ライフにボイドからコア5個
  - リザーブにボイドからコア4個
  を置いて開始する。
- リザーブの4個は **ソウルコア1個 + 通常コア3個** で固定（Ver.17.0 改定）。
  - Ver.17.0 以前は「通常コア4個」を選ぶことも可能だったが、改定によりソウルコア使用が強制化された。
- コアはカード本体そのものではない。
- 同じ「カード上のコア」でも、ルール上の移動先は
  - リザーブ
  - トラッシュ
  - ボイド
  - ライフ
  - 別カード上
  で分かれる。
- そのため、`field -> trash` のようなカード本体移動と、コア移動は分けて実装する。

## 通常コアとソウルコア

- ソウルコアは、通常コアとは別種のリソースとして扱う。
- ルールQ&Aでは、ソウルコアは「ゲーム中に1個だけ持つことができる特殊なコア」とされている。
- ソウルコアは**必須**。ゲーム開始時に必ずリザーブに1個配置する（Ver.17.0 改定で強制化）。
- ソウルコアは、通常コアのように
  - スピリットに置く
  - コスト支払いに使う
  ことができる。
- 自分のメインステップの通常の「コアの移動」では、ソウルコア1個のスピリットと通常コア1個のスピリットのコアを入れ替えられる。
- したがって、通常の「コアの移動」は、少なくともフィールド上の通常移動ではソウルコアを含み得る。
- **generic な「コア」はソウルコアを含む**。公式はソウルコアを除外したいとき明示的に「**ソウルコア以外のコア**」と書く（例: BS41 Q6534〜Q6537）。除外明記が無ければ generic「コア」に soul を含み、どの物理コアを動かすかは**持ち主が選ぶ**（[除去の選択者・Q31528](06b_core-removal-choice.md)、BS35 Q22728: ライフから減らすコアを soul→リザーブ / 通常→ボイドで選べる）。
- **ソウルコアの硬い行き先制約は「ボイド不可」のみ**（BS36 Q5941）。行き先がボイドの generic 効果では通常コア強制で、ライフ/リザーブ/フィールド/トラッシュへは move/place できる（BS74 Q30852、2026-06-09 検証で旧「generic ではライフに soul 置けない」を撤回）。
- 創界神ネクサスへ generic な「コアを置く」処理でソウルコアを置くことはできない（創界神固有制約。soul とは別系統）。
- 逆に、カードテキストがソウルコアを明示する場合は、その個別テキストを優先して扱う。
- 実際に、カードテキストで明示的に
  - `このスピリットの[ソウルコア]を自分のライフに置ける`
  - `自分のリザーブの[ソウルコア]を自分のライフに置ける`
  - `自分の[ソウルコア]を創界神ネクサスの「契約神オメテオトル」に置く`
  のような効果は存在する。
- `封印` 系では、
  - `《封印》『このスピリットのアタック時』このスピリットの[ソウルコア]を自分のライフに置ける`
  - `《封印》『このスピリットの召喚時』自分のリザーブの[ソウルコア]を自分のライフに置ける`
  という代表例があり、explicit `[ソウルコア]をライフに置く` は名指し版。generic な `コア1個をライフに置く` でも soul を選べる（除外は「ソウルコア以外」明記時のみ）。
- 同様に、少なくとも「創界神ネクサス」も
  - generic な `創界神ネクサスにコアを置く` では不可
  - explicit な `[ソウルコア]を創界神ネクサスに置く` なら可
  の両方が存在する。
- また、`〖ソウルドライブ〗` のように `[ソウルコア]をゲームから除外する` 事象は存在する。
- このとき Q&A では、除外したソウルコアは
  - ボイド
  - ライフ
  - リザーブ
  - フィールド
  - トラッシュ
  の他のコアと混ざらないよう、それ以外の場所に置くとされている。
- したがって、`ゲームから除外する` は `ボイドに置く` とは別処理として実装する。
- ソウルコアの移動禁止先と explicit 例外の最終整理（2026-06-23 §41-42/§54 と整合化）:
  - **ボイドは常に不可**。explicit 指定でも soul をボイドに置けない。
  - **創界神 / 創界石は generic では不可、explicit 指定で可**（実例: `[ソウルコア]を創界神ネクサスに置く`）。
  - **ライフ / リザーブ / フィールド / トラッシュは generic / explicit ともに可**（§41-42・§54。2026-06-09 検証で「generic ではライフに soul 置けない」を撤回）。
  - `ゲームから除外する` は `ボイド` とは別処理（ソウルドライブ等）。
- 「ソウルコアをトラッシュに置く」「リザーブのソウルコアがないとき」「トラッシュのソウルコアがあるとき」のようなカードテキストがあるため、ソウルコアは少なくとも
  - フィールド上のカード
  - リザーブ
  - トラッシュ
  に存在し得る。

## ソウルコア移動効果による自己消滅 (Ver.17.0 追加)

- 【起導】等のソウルコア移動効果により、効果の発揮元自身が消滅しても、その効果は発揮可能。
- ただし、消滅や Lv 低下により効果発揮不可 Lv になった場合、以後の「そうしたとき」「バースト発動後」効果は発揮できない。
- 例: 【起導】でソウルコアをトラッシュに置いて効果を発揮 → 自身が消滅 → 起導の主効果は発揮可能。しかし主効果後の「そうしたとき」効果は、消滅により Lv が足りなくなっていれば不可。

実装メモ:

- 起導効果の解決中に自己消滅が発生した場合、主効果は解決を続行する。消滅後の Lv スナップショットを参照し、「そうしたとき」「バースト発動後」の Lv 条件を判定する（未達なら後続効果スキップ）。
- `soulCoreAttached: boolean` だけでは、ゾーン・支払い使用済みか・ライフ/リザーブ/トラッシュ/ボイド上の所在を表せない。ソウルコアの実位置を追えるモデルで実装する。
- **ソウルコア複数個対応（裁定 2026-06-14、移動の追補 2026-09-04）**: モデルは**通常コアと同様＝ロケーション別カウントで保持**（**個体識別は不要**・互いに交換可能）。要求・コストの「《ソウルコア》を要する／置くことで」は**数指定なし＝1個で充足／数指定あり＝その個数**。
- ただし移動命令の「自分の《ソウルコア》を〜に置く」は、数指定がなければ**移動可能なソウルコアをすべて**移動する（ボイド不可・効果耐性などの既存移動不能条件は除く）。これは要求充足数の規則とは別である。[[project_soul_core_future_multiple]]
- ただし《転醒》の「このカードに自分のソウルコアを置いて裏返せる」型は公式 FAQ Q1282/Q1296 により個別扱い。自分のフィールド/リザーブ/トラッシュ/ライフにあるソウルコアを**可能な限り置いてから裏返す**。効果等でソウルコアを置けない場合でも《転醒》自体は発揮でき、B 面の最低 Lv コスト未達なら転醒後に消滅する。

## ボイドの初期コアプール

- ボイドには各プレイヤーにつき通常コア200個が用意される（ソウルコアは別途1個）。
- ゲーム開始時にライフ5個+リザーブ4個をボイドから取るため、ボイドには1人あたり191個が残る。
- 2人対戦の場合、ボイドの初期コア = 200×2 − (5+4)×2 = 382 個。
- コアステップで毎ターン1個ずつリザーブへ移動する。
- ボイドは共有リソースであり、両プレイヤーが同一のボイドからコアを取る。

実装メモ:

- `initializeGame()` で `CORES_PER_PLAYER(200) × playerCount − 初期配分` をボイドに設定済み。
- HUD に各プレイヤーのリソースとしてボイド残数を表示。

## 汎用コア移動

- コアステップでは、ボイドからコア1個を自分のリザーブへ置く。
- リフレッシュステップでは、トラッシュのコアをリザーブへ戻す。
- リフレッシュステップでは
  - 疲労状態のスピリットを回復させる
  - 自分のトラッシュにあるコアすべてをリザーブへ戻す
  の2つを行う。
- トラッシュは
  - 使用したマジック
  - 破壊されたカード
  - 召喚/配置/使用に使ったコア
  - 効果でトラッシュに置かれたコア
  の置き場でもある。
- 効果の指定がない限り、トラッシュのコアはリフレッシュステップで必ずリザーブへ戻す。
- ライフ減少は、「ライフのコア1個をリザーブに置く」という表現で扱う。
- ライフのコアをリザーブに置く処理は、ルール上は「コア除去効果」とは別扱い。
- 現時点の暫定整理として、generic な `ライフのコア1個をリザーブ / フィールド / トラッシュに置く` は、
  - 移動先がソウルコアの通常移動可能先であり
  - 効果文に `[ソウルコア]以外` のような制限がない
  なら、ライフを持つ側が通常コアかソウルコアかを選ぶ実装が最も自然。
- これは
  - Q519 の `generic な to void ではソウルコア不可`（旧記述では to life も含めていたが 2026-06-09 検証で撤回。§41-42・§54 参照）
  - Q520 の `通常のコアの移動ではソウルコアを含み得る`
  - `自分のライフのコア1個をこのスピリットに置く`
  - `相手のライフのコア1個を相手のリザーブに置く`
  - `相手のライフのコア2個を相手のトラッシュ/ボイドに置く`
  - `自分のトラッシュの[ソウルコア]以外のコア1個を自分のライフに置く`
  という実例を合わせた実装寄りの整理である。
- ただし、「ライフに通常コアとソウルコアがあるとき、generic な `ライフのコア1個` で必ず持ち主が選ぶ」と明記した単独の Q&A 本文は、まだ直接確認できていない。
- スピリットが破壊や消滅で場を離れても、カード本体とコアの移動先は同一とは限らない。
- 破壊時のコア移動先は通常リザーブだが、カード効果でボイドなどへ上書きされることがある。
- 相手のカードやコアを移動する効果は、置き先に「相手」と書いていなくても、基本的には相手側のリザーブ/ボイドへ動く。

実装メモ:

- `moveNormalCores(from, to, amount)`
- `moveSoulCore(from, to)`
- `getAvailableLifeCoreMoveChoices(playerId, destination, effectKind)`
- `moveLifeCoreByEffect(playerId, destination, effectKind, chosenCoreKind?)`
- `resolveLifeDamage(playerId, amount)`
- `refreshTrashCoresToReserve(playerId)`
- `resolveCardLeavesFieldCores(instanceId, override?)`
  のような共通APIを用意すると、個別処理の重複を減らしやすい。
- 特にライフ混在時は、
  - generic
  - explicit な `[ソウルコア]`
  - `[ソウルコア]以外`
  と、移動先による destination restriction を分けて扱える設計が安全。
- 特に `カードが場を離れる` ときは
  - 通常コアは `reserve / trash / void`
  - ソウルコアは `reserve / trash / removed_from_game`
  を別に指定できる形が安全。
  generic な「コアをボイドへ」の制約と、ソウルコアの例外移動を分けやすいため。

## コスト支払い

- 軽減で確定した `reducedCost` は、支払い前に固定する。
- 支払いソースは、少なくとも
  - リザーブ
  - 自分の場のカード上コア
  を扱える必要がある。
- ソウルマジックのように「ソウルコアだけで使用できる」条件付き支払いもある。
- 支払い後にコア不足になったカードは、コスト支払い起因の消滅待機へ入る。
- 支払うカードコストは、使用するカードを提示した時点で決定される。
- 軽減元に数えたスピリットやネクサスからコアを支払って消滅しても、軽減はそのまま有効。
- 支払いに使ったコアはトラッシュへ置かれ、通常は次のリフレッシュステップでリザーブへ戻る。

実装メモ:

- 現状の `rules-core` では
  - `calculateReduction()`
  - `getAvailableMagicPaymentSources()`
  - `useMagicCardAsAction()`
  - `getHandWrittenEffectResolver(cardNo)`
  - `moveNormalCores()`
  - `moveSoulCore()`
  - `getAvailableLifeCoreMoveChoices()`
  - `moveLifeCoreByEffect()`
  - `refreshTrashCoresToReserve()`
  - `resolveLifeDamage()`
  - `resolveCardLeavesFieldCores()`
  で、軽減確定、支払い候補列挙、コア移動の共通API、支払い起因消滅の骨組みまでは入っている。
- さらに、`hand-written-effect-resolvers.ts` で
  - `ライフのコア1個をこのスピリットに置く`
  - explicit な `[ソウルコア]`
  - `[ソウルコア]以外`
  の代表例を `useMagicCardAsAction()` 経由で通せるようになっている。
- その resolver 本体は `EffectActionContext` ベースに寄せてあり、`magic` 以外の source-kind にも流用できる前提になっている。
- その `EffectActionContext` には `chosenLifeCoreKind` を載せられるので、generic なライフ移動で通常/ソウルの両方が候補になる場面でも、action 層から選択を渡せる。
- さらに `useFieldCardEffectAsAction()` により、少なくとも `spirit / nexus / system` の source kind から shared resolver を通す土台がある。
- `getLegalActions()` も `availableChosenLifeCoreKinds` / `requiresChosenLifeCoreKind` を返せるため、field-card effect の合法手列挙からこの選択要否を表現できる。
- ただし、現時点の支払い処理は「どの通常コアを払うか / ソウルコアを払うか」の明示選択UIまではまだ持っていない。
- また、leave-field override は `queuePendingLeave()` と `createTargetCardPendingLeaveResolver()` を通じて、少なくとも hand-written resolver から自動発行できる。
- ただし、カード本文からの DSL 自動解釈まではまだ入っていない。

## 推奨データモデル

最終的には、少なくとも次のどちらかへ寄せる。

### 案A: 軽量カウント + 明示的ソウルコア位置

- `CardInstance.normalCoreCount`
- `PlayerState.reserveNormalCores`
- `PlayerState.trashNormalCores`
- `PlayerState.lifeCoreCount`
- `SoulCoreState.location`
  - `card(instanceId)`
  - `reserve(playerId)`
  - `life(playerId)`
  - `trash(playerId)`
  - `void`
  - `removed_from_game`

### 案B: CoreLocation ベース

- `CoreStack[]`
- 各スタックが
  - `kind = normal | soul`
  - `location`
  - `ownerPlayerId`
  を持つ

MVP では案Aの方が実装しやすい。
ただし、ライフ上のソウルコアや、ソウルコアだけを参照する例外効果を増やすなら、案Bの方が自然になる。

検証結果としては、案Aでも次を明示的に持つ必要が高い。

- ~~初期配置時にソウルコアを使うかどうか~~ → Ver.17.0 で強制化。選択不要
- 現在のソウルコア位置
- generic な core move では移動できるが、generic な `to void` / `to genesis` では移動できない、という制約（`to life` は 2026-06-09 検証で generic 可へ撤回。§41-42・§54 参照）
- 創界神ネクサスについては explicit な `[ソウルコア]` 指定で例外が存在すること
- `ゲームから除外する` は `void` とは別ゾーン/別状態として扱う必要があること
- トラッシュのコアが通常コアだけでなくソウルコアも含み得ること

## このプロジェクトでの実装方針

1. カード本体移動とコア移動を分ける（実装済み）。
2. ソウルコアの位置を追える（実装済み）。
3. ライフ減少 / リフレッシュ時のコア回収 / ボイド参照 / 創界神など特殊なコア配置先。
