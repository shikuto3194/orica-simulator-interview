# バースト関連ルール

親文書: [04_state-based-rules.md](04_state-based-rules.md)。サイズ上限超過に伴い分離（2026-06-12）。バーストの宣言・解決タイミングと追加ルールを集約する。

## 公開カード自身による空き枠へのセット

公式マニュアル[エターナル page12](https://www.battlespirits.com/rule/official-rule-manual-eternal/page12.html)
「バーストエリアにはバーストを1枚しかセットできません」（A、2026-10-16確認）。
BSTH09-M01の「自分のバーストがセットされていなければ、セットできる」は、
同時に公開された複数枚のうち同じ所有者の枠へ1枚まで選ぶ。通常セットのターン制限や
既存セットの破棄・交換を、この自己効果へ追加しない。選択時にも空き枠を再検査する。

カード自身の任意効果の選択者は所有者とし、選択後は元のオープン効果の選択者へ戻す
（[任意効果](03c_effect-text-interpretation.md)の適用、B）。
M01の原因系統には「自分の効果」の限定がないため、相手効果も条件を満たす。
回帰は `bsth09-m01-revealed-burst-slot.test.ts`、GUI/RESTは
`?scenario=revealed-burst-slot`（`owner=bob&foreign=1`で相手による公開）。

## 待機状態とバースト誘発

- バーストや「フィールドを離れたとき」誘発は、待機から実離脱までの間を区別して処理する必要がある。
- 公式ルールマニュアルの `バーストおよびバースト効果の説明` では、バースト条件を満たしても、その時点でほかの効果が解決中なら先にそれらをすべて解決し、その後にバースト効果を発揮する。
- バースト条件を満たした時点では、カードはまだ `セットされているバースト` の状態。
- バースト発動宣言が成立した後、効果発揮待ちのバーストは burst area 上で表向きの `バースト状態` として扱う。engine 上では `setBurstStates` から外し、`revealedBurstStates` で追跡する。
- 実際のバースト効果解決は burst area 上の `バースト状態` で行い、解決後も burst area に残っていれば通常はトラッシュへ移動する。
- engine 上では、`burst:revealed` を `burst:resolve-main:start` より先に出し、発動宣言成立後から resolver 実行中まで `revealedBurstStates` で追跡するのが自然。

### バースト破棄の対象と発動成立の境界

（2026-09-04 ユーザー確認、信頼度 C。宣言応答中のセット扱いは独自 Q&A
`external-qa/qaData.js` qa-012 と整合。）

- 発動宣言に対するスタック窓では、表向きでも発動はまだ成立しておらず、セット中の扱いを維持する。**発動成立後にセット中でなくなるのは正しいが、発動宣言への応答窓を開く前に外してはならない。**
- 「相手のバースト1つを破棄する」（BSRK01-C06）は、セット中のバーストと、発動宣言への応答中のバーストを対象にする。破棄したカードはトラッシュへ移動する。手札などから直接発動宣言したものも、トラッシュへ移動して発動を止められる。
- トラッシュから発動宣言するバーストは、破棄してもトラッシュにあるままなので、この破棄では発動を止められない。
- 発動成立後のバースト効果発揮宣言まで進んだものは破棄対象にならない。他にセット中のバースト等がなければ対象なしで不発となる。
- 実装は `RevealedBurstState.activationPending` で宣言応答中を区別し、`getDiscardableBurstStates` で候補を共通化する。BSRK01-C06 の効果選択 UI と検証は root `needs-ruling.jsonl` を参照。

## バースト発動宣言タイミング (Ver.17.0 改定)

- **バースト発動宣言は、手札誘発効果と同じタイミングでのみ可能**。
  - Ver.17.0 以前: 条件を満たしてから解決直前までいつでも宣言可能だった。
  - Ver.17.0 以降: 手札誘発効果の宣言窓でのみ宣言可能に縮小。
- engine 上では、同じタイミングの非公開キューのうち先にバースト発動キューで「発動する/しない」を選択し、その後に他の非公開キューの「発揮する/しない」をすべて確定する。バースト発動宣言への応答窓は、それらの非公開キューが完了してから開く。
- バースト効果の解決タイミングは変更なし（他の効果をすべて解決後）。
- 複数バースト発動時: 宣言順が解決順となる。
  - **防御側優先との関係（確定: 公式マニュアル[エターナル] page12/page14、信頼度 A、2026-06-12 取得）**:
    防御側優先は「宣言順序」のルールとして整理された。page14 FAQ 原文:
    「発動する条件を満たしたら、その効果から誘発する効果と同じタイミングで**ブロック側から**発動の宣言をしなければいけません」。
    page12 原文: 「複数のバースト効果が発動していたときは、**発動した順番に**効果を解決してください」。
    つまり同一窓ではブロック側（防御側）が先に宣言する義務があり、解決は宣言順 — 両ルールは矛盾しない。
    旧 FAQ Q5715（BS34-054）「同時に発動しようとした場合、ブロック側が先に発動」とも整合。

派生・内部の「効果発揮後」・通常バーストの解決順は [04b5](04b5_after-effects-and-burst.md) を参照。

## 相手の効果による相手の手札増加（2026-09-14）

ユーザー指定裁定、信頼度 **C / 実装採用**。「相手の効果によって相手の手札が増えた後」は、
**相手自身の効果でカードが相手の手札に入った事実**に反応する。効果前後の総数差で判定しない。

- ドロー（その後の破棄を含む）、1枚破棄することでトラッシュから1枚回収、オープン札を加える処理、その他の「加える／戻す」は条件成立。
- 「入れ替え」は不成立。1枚と2枚など非対称でも同じ。入れ替えとは別に行うドローは条件成立。
- 手元の増加、通常のドローステップ等の効果によらない増加、バースト所有者の効果による相手手札増加は不成立。
- 実例: BSGE01-CX01 神薙 ユウの初回バレットエディットは「手札1枚を下へ置く→1ドロー」なので、BSTS01-R02 ソウエイの条件を満たす。後の下カードとの入れ替えは満たさない。
- 実装は共通ゾーン移動・効果アクション境界で手札に入ったカードを記録し、交換で入った分だけを除外する。原因は手札が増えた側の視点なので、この条件の登録は `self_effect`。

同じオープン処理で自己回収と通常回収が重なる場合の事象選択・宣言機会は、[同時手札増加とバースト](04b4_simultaneous-hand-increase.md) を参照（公式 Q484 / Q7927）。

## 手札からの直接バースト発動（裁定 2026-06-16, 信頼度 C / ユーザー確認）

「手札にあるこのカードは、バースト条件を満たしたとき（〜なら）発動できる」型（BSTS01-M01[2]『〔ゲームに1回:同名〕… 自分のカウント5以上なら発動できる』）。バーストエリアへの事前セットを経ず、手札のカードを直接バーストとして発動する機構の確定裁定。

- **発動宣言タイミング = 通常バーストと同じ**（手札誘発効果と同窓・Ver.17.0）。通常バーストと同列に扱い、相手アタック後トリガーの自動発動機会も**通常バーストと同じ**（窓でプレイヤーが宣言）。
- **発動条件（カウント5以上等）の判定は発動宣言時**。
- **公開するのは発動したそのカードだけ**（2026-09-14 ユーザー確認、C / 実装採用）。セット中ソウエイがあっても、手札からランガを発動したならランガだけを公開する。GUI のセット枠の反転は所有者一致ではなくカードID一致で判定する。
- **発動するとこのカードは「バーストゾーンで発動した」扱い**にする。ただし GUI 上で実際にバーストゾーンへ置くと（通常バーストと）競合するため、**ゾーン移動は内部状態のみ**で扱い、視覚配置はしない。
  - 発動後の行き先は**バースト効果本体が決める**。BSTS01-M01[4,5] は最終ステップで「このカードをコストを支払わずに召喚する」（burst→self-summon パターン、R02/X03 同型）ため、**このカードはフィールドへ出る**（トラッシュ行きではない）。バースト効果が自己召喚を含まない手札ソース型のときのみ、通常バースト同様「バーストゾーン相当に残ればトラッシュ」が適用される。
- **〔ゲームに1回:同名〕= 1ゲーム通算1回**（同名カードでゲーム全体を通じて1回）。

## セット中バーストの追加発動条件（裁定 2026-07-23, 信頼度 C / ユーザー確認）

「セットしているこのカードは、自分のスピリットがアタックしたときに発動できる。」型（BSGE01-M03『雨宮ツバキ』/ BSGE01-M04『竹田ヒバリ』、【バースト】ヘッダ直前に空行を挟んで配置）。両カードとも `printedCategory:"spirit"` で `mirageData` を持たない。

- **「セットしているこのカード」＝バーストゾーンにセットされている本カード自身**を指す（既存 `applicability.zone:"burst_set"` 語彙、BSTH01-M13 等と同型）。ミラージュ機構とは無関係。
- 直後の【バースト：〇〇後】効果本体を、**通常のバースト条件を待たずに「自分のスピリットがアタックしたとき」にも追加で発動宣言できる**、というバースト追加発動条件を意味する。
- **解決順の制約**: 通常のアタック誘発効果（『アタック時』「アタックしたとき」等）より先に解決することはできない。
- **アタックしているスピリットの不在チェック**: アタック誘発効果の解決中にアタックしているスピリットがいなくなれば発動できない。[手札からの直接バースト発動](#手札からの直接バースト発動裁定-2026-06-16-信頼度-c--ユーザー確認)の宣言タイミングに準じ、[相手アタック後バースト（05b:108）](05b_multi-attack-designated-attack-lifecap.md)「そのバースト解決前にアタックしたスピリットがフィールドを離れていたら、そのバースト自体が発動できない」と同型の裁定。

実装メモ（実装済み、2026-07-23）:

- `BurstTrigger.own_attack`（`{ kind: "own_attack"; player: EffectPlayerRef }`）を新設。attacker 自身向けの `pendingBurstCheck` を積む専用経路 `maybeQueueOwnAttackBurstCheck`（`attack-burst-flow.ts`、`advanceAttackDeclarationStateIfReady` から `maybeQueueAttackAfterBurstCheck` と並列に呼ぶ）で配線した。
- 「通常条件 OR 自分アタック時」は `timing.burst.trigger` を配列化せず、同一バースト本体の steps を2つの effects エントリ（通常条件の trigger と `own_attack` trigger）で共有する形で表現する（BSGE01-M03 参照。card-data 側で `EffectStep[]` の共有 const を用いる）。
- `own_attack` の structured event family は `action_declared`（`action_after` とは別）。`attack_finished`（`attack_after`）と matcher レベルで名前空間を分離しており、将来 `attack_finished` に `player:"self"` 型カードが追加されても誤マッチしない（`own-attack-burst-trigger.test.ts` で固定）。
- BSGE01-M04 の通常バースト条件「フィールドを離れた自分のスピリットが魂状態になった後」は `BurstTrigger.enter_soul_state`（`{ kind: "enter_soul_state"; player: EffectPlayerRef }`）を新設して表現した。既存の card_event `enter_soul_state`（F2, ENIGMA「魂状態になったとき」、`player.soulStateInstanceIds` の diff 検出）と同じ検出ブロックを `mapTriggerEventToBurstCheck` 経由で burst 経路にも流用しており、専用の differ は追加していない。
  - **「フィールドを離れた」限定**: 汎用 enter_soul_state 検出は field-exit-replacement 経由（zone 不変）と BSLH01-CX01 型の手札/手元からの直接魂状態化（hand/set_aside→field へ zone 変化）の両方を無差別に拾うため、`CollectedTriggerEvent.fromZone`（enter_field 系で既存の SSOT フィールドを流用）に魂状態化直前の zone を積み、`mapTriggerEventToBurstCheck` 側で `fromZone === "field"` のときのみ burst check を生成する（adversarial verifier 2026-07-23 round1 指摘）。
  - **「自分のスピリット」限定**: `own_attack` と同様 `triggerFilter: { category: ["spirit"] }` を付与するが、enter_soul_state の対象カードはチェック評価時点で既に魂状態化済みのため、`matchesCardFilter` の既定挙動（`soulState` 未指定時は魂状態カードを除外、card-filter.ts:264-270）により黙って不一致になる罠がある。`triggerFilter.soulState: "include"` を明示しないと発動条件そのものが死ぬ（own_attack の attacker は魂状態でないため不要、enter_soul_state 固有の注意点）。
- `own_attack` にも `triggerFilter: { category: ["spirit"] }` を付与し、アルティメットのアタックでは発動しないようにした（原文が「自分の**スピリット**」限定のため、BSGE01-M03/M04 双方、adversarial verifier 2026-07-23 round1 指摘）。
- BSGE01-M04 のバースト本体（重疲労＋デッキ5枚オープン→ミラージュ緑/青コストなしセット＋緑/青ブレイヴ1枚手札）に伴い、`DeckRevealPick.destination` に `"mirage_set"` を新設（`mirage-system.ts` の `applyFreeMirageSetBookkeeping`）。`mirageSetStates` は1プレイヤー1枠固定のため pick は `count:1` とし、複数該当時は1枚のみセットする（既存ミラージュがあれば手札に戻る、`useSetMirageAsAction` と同じくターン1回制限の対象外・`handCount` 変更なし）。
- 詳細は `autorun-queue/needs-ruling.jsonl`（BSGE01-M03/M04、resolved）参照。

## バースト追加ルール

- バーストの発動は「マジックの使用」ではない。「マジックの使用を制限する」効果はバースト発動を妨げない。
- バーストではないカードをバーストエリアにセットした場合、そのバーストが公開された時点でセットしたプレイヤーの敗北となる。
- バーストカードには、バースト効果のほかに追加効果（「その後」以降のテキスト）を持つものがある。追加効果はバースト効果解決後に続けて解決する。
  - 追加効果はバースト条件を満たさなくても発動する場合がある（カードテキストに依存）。

実装メモ:

- `isBurstActivation` と `isMagicUse` を明確に分離する。
- 不正セット検知は `revealBurst()` 時に `card.hasBurstEffect` をチェックし、false なら即敗北処理。
- **実装済み**: バースト発動宣言窓: 手札誘発効果と同じタイミングに制約する（Ver.17.0 改定）。条件成立時に発動可否を確定し、効果発揮宣言は派生効果をすべて解決した後まで待機する。
- **実装済み**: 複数バースト発動時: キュー順（≒宣言順）で解決順を決定。防御側にバーストチェックがあれば防御側が先に宣言（`current-actor.ts` step 6 / `getAvailablePendingBurstCheckLegalActions`）— 公式「ブロック側から宣言」と整合確認済み（2026-06-12）。
- 追加効果は `burstFollowUpEffect` として burst resolver に組み込む。
