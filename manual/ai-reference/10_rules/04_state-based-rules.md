# State-Based Rules

## 基本方針

フィールドから離れる処理は、即座に

- `field -> trash`
- `field -> hand`

のように動かさず、いったん待機状態を経由する。

## 待機状態

待機状態は、フィールド離脱が確定したが、まだ最終移動が終わっていない途中状態。
「フィールドを離れるとき」効果は、離脱理由に関わらず共通で参照される。
理由ごとの区別（『破壊時』『消滅時』、「手札/デッキに戻るとき」等）は個々の効果テキストで行う。
「フィールドを離れたとき」効果は実移動後の `leave_field` 境界だけを見るため、DSL では `game_event` の `exactEventKind:true` を付ける。

同一効果の成立結果と別効果の待機状態参照は [04e](04e_leave-outcomes-and-trigger-eligibility.md) を参照。

### 離脱理由と移動先

| 理由 | `pendingLeaveKind` | 通常の移動先 | 備考 |
|------|-------------------|------------|------|
| 破壊 | `destroy` | トラッシュ | 効果やバトル結果による |
| 消滅 | `vanish` | トラッシュ | コアが最低Lv未満になった結果 |
| バウンス | `bounce` | 手札 / デッキ / 手元 | 破壊との差は理由と移動先 |
| 除外 | `remove_from_game` | ゲーム外 | field は待機、field 外は直接 |

`手札に戻す。この効果で戻した〜` のような省略テキストでは、`戻した〜` 以降の処理は、対象がバウンス待機状態になってから解決する。

### `pendingLeave` を立てる / 立てない境界

field離脱は `queuePendingLeave()`。`move_card`: `from.zone === "field"` かつ `to.zone !== "field"`、`field -> trash` は `bounce` + `leaveDestination:{ zone:"trash" }`。`move_self` も待機のみ。対象外: field外起点、field入り/内/下カード化、flush。

実装:

- `pendingLeaveKind`
- `pendingLeaveCause`
- `pendingLeaveChainId`
  を `CardInstance` に持たせる。

### BP比べ破壊の cause 分類（裁定 2026-06-12）

効果が引き起こした **BP比べによる破壊** の直接 cause は「BP比べ」であり「効果」ではない。したがって「効果によって破壊された/フィールドを離れた」系トリガーは発火しない。

「自分/相手によって破壊」は満たし得る。公式 Q&A Q18316/Q18317 (`external-qa-official/PB12.md`) は、自分/相手による破壊に BP比べ破壊と該当プレイヤーの効果破壊を含め、Lv0 コア不足破壊は除外している。

実装含意:

- BP比べ destroy プリミティブの `pendingLeaveCause` には `"effect"` ではなく `"bp_compare"` 等の専用カテゴリを割り当てる。
- 「相手による」判定は `pendingLeaveCausePlayerId` に BP比較の勝者プレイヤーを記録して行う（効果ソースの controller ではなく **勝者** が cause player）。
- `TriggerEventCause` では、対象カード視点の勝者帰属として `opponent_bp_compare` / `self_bp_compare` に分離する。互換用の総称 `bp_compare` は DSL の明示フィルタで両方にマッチさせる。
- 関連: 相手のコア奪取によるコア不足消滅も「相手による」扱い (`pendingLeaveCausePlayerId` = コア奪取の発生源 controller)。同じ「直接の cause が誰か」原則。

### 全待機状態に共通する制約 (Ver.17.0 統一)

Ver.17.0 改定により、破壊・消滅・バウンス・除外の全待機状態は同じ制約で扱う。消滅待機だけの追加制約は廃止された。

- 待機状態のスピリットのシンボルは**軽減に使える**。シンボル参照も可能。
- 待機状態のスピリットに新たなブレイヴは合体できない。
- 待機状態に入る前から発揮していた常時効果は継続する。
- 待機状態に入った後に新たに発揮できるのは、待機（離脱）に関連する効果のみ。
- 待機状態中でも、カード自身のキーワード能力（例: 【重装甲】）は維持される。

#### 待機状態中のコア除去

- 待機カード上のコアも支払い・維持コア選択やコア除去に使える。コアが減っても再消滅せず、他の待機から消滅待機へ変更しない（[2026-09-04 確定裁定](03f_stack-failure-and-waiting-cores.md)）。

#### 合体ブレイヴ単体破壊

- 合体中のブレイヴのみが破壊された場合、そのブレイヴが合体スピリットに与えていた色・コスト・BP+・シンボル・合体中効果の付与は即座に停止する。
- 合体スピリット本体はフィールドに残る。

#### 待機状態中の場唯一性バイパス（裁定 2026-06-12）

「場に同名は1体だけ」「場に1個だけ」等の場唯一性制約は、既存個体が**離脱 pending（待機状態）中の間だけ**一時的にバイパスされる。静的に並ぶ状態では依然として禁止。

- **対象 pending**: 破壊待機 / 消滅待機 / バウンス待機 / 手札戻し・デッキ戻し・トラッシュ送り・set_aside 等、離脱が確定しているが flush 前の全 pending
- **バイパスが効く2系統**:
  1. **召喚行為内の自壊によるウィンドウ**: 既存個体が新規召喚のコスト支払いや維持コア選択不能で消滅待機に入ると、その召喚アクションの間だけ同枠に 2 体存在できる。  
    典型例: 既に同制約の対象が 1 体いる場合でも、その個体上のコアを全部コスト支払いまたは新個体の維持コア選択に使うと、既存個体がコア 0=消滅待機になり新規召喚が成立する。
  2. **その他 pending 中**: 既存個体が任意のソースで離脱 pending 状態にある間、新規個体を追加で出現可。pending が複数並ぶ間は 2 体以上の共存も許される。
- **静的状態（pending でない）では出現自体不可**: 離脱が flush されるまでの過渡的ウィンドウだけが例外。

実装含意:

- 場唯一性チェックを実装する際、対象スロットの既存個体が pendingLeave 系（destroy/vanish/bounce/return-to-hand/return-to-deck 等）に入っているかを判定し、入っていれば追加出現を許可する。
- 召喚パイプラインでは「コスト支払い→維持コア配置」中に既存個体の消滅待機が発生し得るので、その時点での唯一性チェックは消滅待機を除外側に倒す。
- pending flush 後に 2 体残らないよう、flush 順序（古い個体の離脱完了 → 新個体定着）を保証する。

実装メモ:

- **実装済み**: 軽減計算時、待機状態のスピリットのシンボルを除外しない（`cost-system.ts` の vanish 除外フィルタ撤去済み）。
- **実装済み**: 消滅待機の効果フィルタ特別制約を撤廃（`state-based-actions.ts` の `VANISH_PENDING_ALLOWED_EFFECT_FILTERS` 削除、`getAllowedEffectFilterTags` / `getEffectFilterBlockReason` を全待機状態統一済み）。
- コア不足チェックは既存待機を除外する。残存コアを使っても、元の離脱理由・チェーン・誘発を上書きしない。
- **実装済み**: 合体ブレイヴ単体破壊: `queuePendingLeave()` でブレイヴが待機状態に入った時点で `attachedToInstanceId` / `attachedChildrenIds` を即時解除し、合体スピリットへの付与を停止する。

## 消滅

- 消滅は、スピリット/アルティメットのコアが最低 Lv コスト未満になった状態。
- 旧表現の `Lv0として破壊` とは別管理にした方が安全。
- ネクサスはコアが 0 個になっても消滅しない（Lv1 として扱い続ける）。ただし、Lv コスト上昇効果で最低 Lv コストが上がった場合は、その実効最低コアを満たせなければ消滅する（BS53 Q8424）。

### 消滅待機時の Lv 依存効果の判定

消滅待機に入る時点での Lv が、発揮しようとする効果の Lv 条件を満たすかどうかで発揮可否が決まる。

例: Lv1(1) / Lv2(2) のスピリットにコア 2 個。Lv2 の『相手によるこのスピリットの消滅時』効果を持つ場合:

- **一度に 2 個外された場合（コア 2→0）**: Lv2 の状態から直接消滅待機に入るため、Lv2 条件を満たす → **発揮できる**。
- **1 個ずつ 2 回に分けて外された場合（コア 2→1→0）**: 1 回目でコア 1 個（Lv1）になり、2 回目でコア 0 個になって消滅待機に入る。消滅待機に入る時点の Lv は 1 なので、Lv2 条件を満たさない → **発揮できない**。

同様に「このスピリットが相手によってフィールドを離れるとき」も Lv 条件付きなら同じ判定になる。

実装メモ:

- **実装済み (P3-83)**: `runStateBasedActions` がフィールドの安定スピリットの実効 Lv を毎パス
  `pendingLeaveLvSnapshot` にローリング記録し、消滅待機へ遷移した瞬間の直前値で凍結する
  （一括移動 2→0 は Lv2、1 個ずつ 2→1→0 は Lv1）。
- **実装済み (P3-83)**: 実効 Lv の正源は `getEffectiveLevel` 1 つで、`pendingLeaveKind==="vanish"` の間は
  snapshot を返す。表示・effective identity（`getEffectiveLevel` / `getEffectiveBp`）と Lv 条件評価
  （`min_level` / `applicability.level` を担う `getCardCurrentLevel` は `getEffectiveLevel` へ委譲）が
  同一値を共有する。条件評価は元々現在コアから直接算出する別実装で、表示だけ直すと『消滅時』Lv 条件付き
  効果が Lv0 判定される乖離が残ったため、評価経路を `getEffectiveLevel` に一本化して解消した（SSOT）。
- ~~`allowedEffectFilters = { vanish_related, leave_field_related, suppress_effects }`~~ Ver.17.0 で廃止。全待機状態統一により消滅待機でも全効果タグを受け付ける。
- ターゲット列挙での消滅待機除外は撤廃済み。

## トラッシュ移動の遅延

- 消滅や破壊で待機状態になっても、ただちに移動先へ行かない。
- その離脱による効果と派生効果を解決した後に実移動し、その時点で残存コアをリザーブへ置く。待機入り時には戻さない。
- `flushPendingLeaves()` はグローバルに1回ではなく、**効果チェーンの階層ごと**に走る。

[選択順](04d_leave-choice-timing.md)

### フラッシュのタイミング原則

待機状態のカードが実際にゾーンを移動するのは、そのカードを待機状態にした**原因の効果チェーンが閉じた時点**。
内側のチェーンが先にフラッシュし、外側のチェーンは後からフラッシュする。

スタック応答の離脱完了は[03f](03f_stack-failure-and-waiting-cores.md)参照。

「チェーンが閉じた」には、**プレイヤー入力待ちで中断中の効果解決継続 (continuation: コア配分 /
対象選択 / 維持コア配置 / スタックカスケード等) が残っていない**ことも含む。継続が立っている間は
効果はまだ解決途中なので、待機カードは実移動しない。継続が解決 (resume) して初めてフラッシュする。

実装メモ:

- flush ゲート `canFlushPendingLeaveEntity` は `hasOutstandingEffectResolutionContinuation(state)`
  (SSOT, `state-based-actions.ts`) で継続の有無を見て、残っていれば flush しない。gate 対象は
  resume ハンドラが必ず finalize/flush する継続のみ (= 継続解決時に確実に flush され stranded しない)。
- **各継続の resume ハンドラは解決完了時に `finalizeEffectResolution` を通して flush する**必要がある。
  premature flush を gate で止めた以上、resume で finalize しないと待機が次アクションまで移動遅延する。
  `applyPendingCoreSplitAction` / `applyPendingCoreCountAction` はこれを欠いていたため追加修正済 (P3-108)。
- `runActionMainResolution` は継続生成後も `finalizeEffectResolution` を呼ぶため、誘発収集・神託・
  endLogs は早期に走る。ただし legal-actions は継続解決アクションを誘発解決ゲートより**前**で
  early-return するので、早期収集された誘発は継続解決まで発火できず、解決順は保たれる
  (= 早期 finalize の副作用は flush 以外には観測されない。finalize 委譲の根治は P3-108)。

### 例1: コスト支払い消滅と「この効果発揮後」

マジック（コストn）: `フラッシュ：自分のスピリット1体を回復させる。この効果発揮後、トラッシュにあるカード1枚を手札に戻せる。`

コスト支払いで自分のスピリットXが消滅した場合:

1. コスト支払い → スピリットXが消滅待機に入る
2. 主効果「スピリット1体を回復」を解決
3. 「この効果発揮後」→ トラッシュからカード1枚を手札に戻せる
4. **Xはまだ消滅待機中（トラッシュにいない）** → Xは手札に戻せない
5. マジック効果のチェーン全体が終了 → Xが実際にトラッシュへ移動

コスト支払いはマジック使用の一部であり、Xの消滅待機はマジック効果チェーン全体に紐づく。
そのため「この効果発揮後」の時点でもXはまだトラッシュにいない。

### 例2: 破壊→誘発→バウンスの入れ子チェーン

主効果: `相手のスピリット1体を破壊する`
自分の別カードの誘発効果: `自分が相手のスピリットを破壊したとき、相手のスピリット1体をデッキの下に戻せる。この効果発揮後、自分はデッキの上から1枚ドローできる。`

1. 主効果で相手スピリットAを破壊 → **A: 破壊待機**
2. 誘発効果が発動 → 相手スピリットBをデッキの下に戻す → **B: バウンス待機**
3. Bの派生効果（「フィールドを離れるとき」等）を解決
4. **Bの内側チェーンが閉じる → Bが実際にデッキの下へ移動**
5. 誘発効果の「この効果発揮後」→ 自分が1枚ドロー
6. 誘発効果のチェーンが閉じる
7. **Aの外側チェーンが閉じる → Aが実際にトラッシュへ移動**

ポイント: Bは内側チェーンの終了時にフラッシュ（ステップ4）、Aは外側チェーンの終了時にフラッシュ（ステップ7）。

実装メモ:

- `deferZoneMoveUntilChainEnd=true`
- `flushPendingLeaves()` は effect chain の階層ごとに、そのチェーンの queue が空になった節目で走らせる。
- 各 `pendingLeave` に `ownerChainId` を持たせ、どのチェーンに紐づくかを追跡する。
- チェーンが閉じるとき、`ownerChainId` が一致する pending leave だけをフラッシュする。
- **実装済み (P3-84)**: flush ゲートを、チェーン束縛待機 (`deferZoneMoveUntilChainEnd: true`) について同一
  chainId の `pendingTriggeredEffects` (召喚時誘発等) も見るよう拡張 → 未解決中は flush しない。コスト支払い
  消滅 (`payment-system` が cause `cost_payment` + defer=true で検出済) は使用効果チェーン全体に紐づき召喚時
  誘発まで待つ (例1)。効果由来 SBA 消滅 (defer=false) / 破壊・バウンスは非束縛で自分のサブチェーン閉鎖時に
  「この効果発揮後」より前に移動 (例2)。バーストは移動後 (gate は `pendingBurstChecks` 非対象)。詳細 issues/archive/P3-84。

## アルティメット召喚条件

- アルティメットを召喚するには、カードに記載された召喚条件を満たす必要がある。
- 召喚条件はフィールドの状態に限らず、ライフ数・カウント数など**あらゆるゲーム状態**が条件になりうる（例: `条件: コスト3以上の自分のスピリット`、`条件: 自分のライフが3以下`）。
- 召喚条件はコスト支払いとは別の宣言前チェック。

実装メモ:

- `canSummonUltimate(state, card)` で `summonCondition` を参照する。
- 条件はカード定義側に持たせ、`legalActions` 列挙時にフィルタする。

## 状態ベースチェックの入れどころ

次のタイミングで必ず走らせる。

- コスト支払い後
- 効果 1 件の解決後
- 派生効果キューが空になったとき
- ステップ遷移前

## 最初に実装すべき状態ベースチェック

1. コア不足による消滅
2. 破壊/消滅/バウンス待機への遷移
3. 待機状態中の効果フィルタ
4. 効果チェーン終端での最終ゾーン移動

## 裏向きカードの素性

裏向き（非公開）カードは素性なしの既定、付与は additive、裏向き ≠ 裏面（B面）の混同回避。詳細は [04c_face-down-identity.md](04c_face-down-identity.md)。
