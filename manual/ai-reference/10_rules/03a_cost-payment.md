# Cost And Payment

> 効果解決・割込・無効化ルールは [03b_resolution-and-interrupts.md](./03b_resolution-and-interrupts.md) を参照。

## 軽減の基本

- 軽減は、フィールド上の同色シンボル数で決まる。
- 同色カード 1 枚ではなく、同色シンボル 1 つごとに 1 軽減。
- ダブルシンボルは 2 軽減できる。
- 1 個のシンボルが複数色として扱える場合でも、同時に複数色へは使えない。
  - 原文の `symbol: ["黄導"]` は黄導1個、`["黄", "導"]` は黄1個と導1個。BSTH02.7-CX01 の黄導1は2026-10-12ユーザー確認（信頼度C・実装に使用）。原文rawにも同表記があり、変換時は `symbolColorEntries` で配列要素の境界を保持する。印字個数・実効シンボル・コピー・表示は `getPrintedSymbolEntries()` を入口とする。
  - 実装済み: `SymbolColorEntry` 型を `cost-system.ts` に追加。`FieldSymbolSource.symbolEntries` で物理シンボル単位にグループ化。`calculateReduction()` は単色シンボルを直接割当後、多色シンボルをバックトラッキングで最適色割当。標準カードでは全エントリが単色のため既存動作と同じ。
- シンボルを持たないスピリット状態のブレイヴは軽減に数えない。
- 軽減できるなら必ず軽減する。
- 軽減シンボル `<六>` は赤・紫・緑・白・黄・青のいずれか、`<七>` はそれらと黒のいずれかで1枠を満たす（2026-09-17 ユーザー指定、信頼度 C・実装に使用）。神・導・極だけでは満たせない。1つの供給シンボルを複数の軽減枠に重複使用しない。
- 実装は `getEffectiveReductionSymbolEntries()` で印字・効果による追加・置換後の六/七を受け付ける色集合へ展開し、既存の最大マッチングで割り当てる。回帰: `six-seven-reduction.test.ts`。

実装メモ:

- `calculateReduction(state, card)` はフィールド上の有効シンボル一覧とカード側の軽減要求を入力に、`reducedCost` と `reductionBreakdown` を返す。
- 実装済み: `assertReductionIsMaximal()` (`cost-system.ts`) で各色 `applied == min(requested, available)` を検証。`assertMatchingPaymentAmount()` から自動呼び出しされ、全コスト支払いパスで軽減の最大適用が保証される。

### 「軽減シンボルすべてを満たして召喚/配置できる」

- 裁定 2026-07-15: このギミックは、召喚/配置しようとしているカードの軽減シンボル要求スロット全数を、フィールドの実際のシンボル有無に関わらず軽減成立扱いにする。
- コストは無条件 0 ではない。通常軽減と同じく、支払いコストは `max(0, コスト - 軽減シンボル要求スロット数)` として計算する。
- 例: コスト 7・軽減スロット 3、フィールド供給 0 でも、3 軽減成立として支払いコスト 4。

### コスト軽減下限（floor）

- 「このカードの配置コストは 0 にならない」「N コスト以上支払わなければ召喚できない」は**軽減後コストの下限**を設ける継続自己修飾。軽減後コストを `max(floor, 印字 - 軽減)` にクランプする（軽減シンボル/override/free すべてを通した結果が floor を下回らない）。floor は印字コストを超えない（`min(floor, 印字)`）。
- DSL: `cost_modify` 自己対象 `modifier:{ floor:N }`（専用アクション型を増やさず CostModifier を拡張）。「0 にならない」= floor:1、「2 コスト以上」= floor:2。
- 実装: `calculateReduction()` が `getEffectiveCostFloor()` で対象カードの継続 `cost_modify` 自己ステップから floor を収集（軽減シンボルと同じく手札ゾーンの CE 未登録カードを `card.effects` 直接読み）。SSOT のため availability / resolution / accel 全経路に反映。test: `cost-floor.test.ts`。

### 支払い文脈限定のシンボル扱い変更（whenPayingForFilter）

- 「自分が系統:「夜錆」を持つカードを召喚/配置するとき、このスピリットのシンボルを白/紫としても扱う」(BSSA01-C01/C02/C03) 型。**この treat_as は無条件には適用されない**。BP・表示・通常の色判定では印字どおりで、フィルタに一致するカードの**召喚/配置コスト軽減を計算するときに限り**供給側シンボルが加色される。
- DSL: `treat_as { aspects:["symbol"], whenPayingForFilter:<CardFilter> }`（専用アクション型を増やさず TreatAsAction を拡張）。
- 実装: `whenPayingForFilter` 付き treat_as は継続 CE を登録しない（`executeEffect` の treat_as 分岐が no-op）。`calculateReduction()` が供給側 `FieldSymbolSource.symbolEntries` を構築する際、各 field カードの `effects` を直接読み、支払い対象カード（`options.card`）を `matchesCardFilterByDef` で照合して一致時のみ加色する。SSOT のため `getEffectiveSymbolBundles`（BP/表示）には漏らさない。test: `paying-for-treat-as-symbol.test.ts`。

## コスト支払いの確定タイミング

支払うカードコストは、使用するカードを提示した時点で決定される。以下の 4 段階は、現在の実装で使う支払い額の計算・適用の整理であり、公式が支払い操作をこの順に逐語規定したものではない。

1. **カードの提示（総コストの決定）**: 提示時点で支払うべき総コストが確定。
2. **軽減シンボルの適用**: フィールドの同色シンボルで軽減。軽減で 0 にもなり得る。
3. **余分コスト（追加コスト）の適用**: 「Xコスト余分に支払わなければならない」等の効果がここで加算される。軽減フェーズは既に過ぎているため、余分コストを軽減で減らすことはできない。
4. **コストの支払い**: 最終コスト分のコアを支払う。

公式エターナル Q1783 は「まず軽減シンボルによるコスト軽減を計算してコスト0になり、その後1コスト余分に支払う」と説明し、Q1813 は無償マジック使用でも余分コストが必要とする（信頼度 A、計算に使用）。これらだけでは通常コストと余分コストの実コア移動の先後までは確定しない。2026-09-22 のユーザー確認により、表示・支払い操作は既存の合算方式を維持する（信頼度 C、本プロジェクトの操作方針）。出典と実装照合は [調査記録](../00_meta/source-findings-official-turn-cost.md#2c-2026-09-22-余分コストの計算と支払い操作を区別) を参照。

- 軽減計算と支払いは同時に確定する。
- 支払いでコアがなくなって軽減元のスピリットが消えても、軽減済みコストは維持される。
- 支払いコストが 0 になっても「コストを支払った」ことになる。

実装メモ:

- 先に `reducedCost` を固定し、その後に支払い適用を行う。
- 支払い途中で盤面が変わっても、再計算しない。
- 余分コストは `additionalCostModifiers` として軽減後に加算する設計にする。
- 実装済み: `AdditionalCostModifier` 型を `cost-system.ts` に追加。`ReductionResult` に `additionalCost`, `finalCost`, `additionalCostModifiers` フィールドを追加。`calculateReduction()` が `additionalCostModifiers` パラメータを受け取り、`reducedCost + additionalCost = finalCost` として計算。支払い検証 (`assertMatchingPaymentAmount`, `canFullyPay`) は `finalCost` を基準に判定。legal action 生成時に `additionalCost`, `finalCost` を返す。

## 支払い前に別のマジックを使用する場合（戦力投入）

裁定: 2026-09-12 Telegram message 7204 / inbox 629905067、および同日の対話で解釈確認済み。
信頼度 C（ユーザー明示裁定、本プロジェクトで確定）。対象は BSAZ01-C12「戦力投入」。

1. 元の地球マジックの使用を宣言する。
2. 元のコスト支払い前に戦力投入の使用を宣言し、戦力投入自身の使用コストを支払う。
3. 戦力投入の使用に対するスタック応答を処理し、戦力投入を解決する。
4. 元の地球マジックのコスト支払いへ戻る。
5. 支払えたら、元の地球マジックの使用に対するスタック応答を処理し、元のマジックを解決する。

> 元の地球マジックはコスト支払い前であり、(元のマジックに対する)スタック前であるため、使用がキャンセルされ、カードも移動しない

これは戦力投入の解決後に元の使用コストが不足する場合の裁定。元のマジックは使用扱いにならず、元のゾーンに残る。解決済みの戦力投入の結果は残す。戦力投入への応答を終えても、元のマジックはまだ支払い前・その使用へのスタック前である。元の使用に対するスタック後に今回の不発となる場合は、使用扱いのままトラッシュに置く。宣言自体の違法化は [03f](03f_stack-failure-and-waiting-cores.md) の別判定。

「使用できる」は通常のマジック使用の許可であり、戦力投入の使用コスト・応答窓を必要とする。既存の使用・支払い・スタック・後処理の共通経路へ接続する。実装記録は [P3-160](../../../issues/archive/P3-160/index.md)。

## 支払いソース

- スピリット上のコアは召喚に使える。
- マジック使用でも、リザーブ以外を支払いソースにできる前提で設計してよい。
- 詳細 UI は Q&A 本文に準拠する。
- コスト支払いに使えるのは通常 `リザーブ` / `フィールドのカード上` のコアだけ。ライフ等それ以外の場所のコアは通常のコスト支払いには使えない。
- 待機カード上の残存コアも支払い・維持コアの選択元になる。コスト支払い由来の待機も除外しない。実移動時のリザーブ返却と区別する（[03f 確定裁定](03f_stack-failure-and-waiting-cores.md)）。

実装メモ:

- `availablePaymentSources` は `reserve` / `on_board_cores` / `soul_core_only` 等を返せるようにする。
- 通常コア / ソウルコア / ライフ / ボイド / トラッシュの整理は `06_core-system.md` を参照する。

## 召喚・配置直後のコア配置

- スピリットやアルティメットを召喚したときは、コスト支払い後に別途コアを置く。
- スピリットは最低でも `Lv1`、アルティメットは最低でも `Lv3` を満たす数が必要。
- ネクサスを配置したときも同様にコアを置ける。
  - ただし、置かない場合でもネクサスは `Lv1` として扱う。
- この直後コア配置でも、通常は `リザーブ` / `フィールドのカード上` からコアを移動する。
- ソウルコアも通常コアと同様に、召喚・配置したカードの上に置ける。

実装メモ:

- `cost payment` と `enter-field core placement` を別入力・別処理として持つ。
- BSTH07.8-X01【界放：3】の3コアは維持用に持ち越し、召喚コストは通常元から別に払う。最低Lvを満たせば追加配置0個でよい。導界者と移動済み3コアは通常の支払い元にしない（Telegram 629905089、2026-10-10、信頼度C・実装に使用）。
- `summon` は `minimumEnterFieldCoreCount >= minimumRequiredCores` を満たさないと確定できない。
- `place_nexus` は、配置時点での最低Lvコストを満たすコア数が必要。標準ネクサスはLv1コスト0のため通常は0コアで確定できるが、Lvコストを増やす効果が適用されている場合は、その増加後のコスト分を満たす必要がある。
- 創界神グランウォーカー / 創界石グランストーンネクサスのような例外は、`enter_field_core_placement_forbidden` のようなタグで通常の `place_nexus` から分岐できるようにする。
- 実在カード例として、`BS58-X09` / `BS59-X09` / `BS61-X09` や `BS58-071(A)` / `BS59-071(A)` のような cardNo は shared registry で `forbidden` 扱いにしておくと、タグ未整備データでも legal action / runner の両方を揃えやすい。

### 「Lvコスト」の対象フィルタとしての用法（調査メモ 2026-07-14）

- 「Lvコスト」は本節の「レベルアップに必要なコア数」（`LevelDefinition.requiredCores`、`levelCostDelta` 修飾込みの実効値）と同一用語。カード印字テキストでは「相手のスピリット/アルティメット…のLvコストを+N」のように**コスト変更効果**の対象として頻出するほか（実装: `override_properties.levelCostDelta`、`level-cost-delta.test.ts`）、**対象フィルタの修飾語**としても使われる。
- 例: BSGE01-C16 / BSTH001-C05 / BSTH002-M02（いずれも textLines 末尾のスタック効果）の「最低Lvコスト1の相手のスピリット/アルティメット2体」は、`levelDefs[0]`（最低 Lv、実効 `requiredCores` 込み）が `1` であるカードのみを対象とするフィルタ条件と解釈する（信頼度 B: `03a:77` 「最低Lvコスト」表現・`04_state-based-rules.md:105` 「コアが最低 Lv コスト未満」表現との用語一致から）。上記 3 枚とも独自カードサイトの Q&A/errata ミラーに該当エントリなし、カード本文のみが根拠。
- この 3 枚のスタック効果本体（対象 2 体選択 + コアをリザーブへ「1 個(ずつ)になるまで」移動 + アタックステップ限定）は実装済み（2026-07-14）。`CardFilter.lv1RequiredCores`（印字 `levelDefs[0].requiredCores` 一致、`levelCostDelta` 実効値は未対応）+ `step.repeat`（対象 1 体ずつ独立解決）+ `core_move`（`amount: {source:{kind:"cores_on",location:target_card}, offset:-1}`）で表現。詳細は `needs-ruling.jsonl`（cardNo: `BSGE01-C16` / `BSTH001-C05` / `BSTH002-M02`、`status:"resolved"`）を参照。

## 手札から使用する行為の標準パイプライン

マジックを基準に、次の順序を標準化する。(batspi.com `https://batspi.com/index.php?マジック&word=BS16-073` 信頼度 A)

1. 使用の宣言とカードの提示
2. 軽減の適用とコスト支払い
3. 対象の選択
4. 主効果解決 (効果の発揮)
5. 派生効果解決
6. カードの後処理
7. トラッシュ移動

**各ステップでのカードゾーン**:

- ステップ 1 (使用の宣言とカードの提示): 通常経路ではカードは手札から出る → `in_use` ゾーンへ。コスト支払い完了後も `in_use` のまま。
  - 戦力投入による支払い前の中断では、元のカードは元のゾーンで保留し、使用キャンセル時も移動しない（上記「支払い前に別のマジックを使用する場合」）。
  - 「支払い完了後は手札にない」(ユーザー確認済み)
  - batspi.com にはステップ 2-5 の間の正確な物理位置の明記はないが、「提示」で手札から出ていることを前提とする。
- ステップ 4-5 (解決中): `in_use` のまま。
- ステップ 7 (後処理後): `in_use` → `trash` に移動。

スピリット/ネクサス召喚・配置でも同様に、宣言時に手札から出て `in_use` → フィールドの流れになる。
スタック窓後の必要コア不足では召喚を成立させず、`in_use` からトラッシュへ移動する。宣言自体が違法になった場合のみ宣言・支払いを取り消し、スタック効果の結果は残す（[03f](03f_stack-failure-and-waiting-cores.md)）。

実装メモ:

- `effectChainId` を発番する。
- 派生効果キューが空になるまでカード本体の最終移動を遅延する。
- `Zone` 型に `"in_use"` を追加して、宣言後・解決前の状態を表現する。
- 使用途中の実ゾーンと、召喚・使用の元ゾーンは区別する。`moveCardZone` が `inUseSourceZone` を記録し、召喚イベントとカード自身のコスト適用ゾーンは共通の `getCardUseSourceZone` を参照する。手札枚数・通常の効果対象は実ゾーンのまま（BSTH07.8-XX01/X01、2026-10-02回帰）。
- `in_use` にあるカードは `"hand"` として扱わない (手札枚数にも含まない)。
- `in_use` にあるカードは、手札やフィールドなどゾーン指定の効果対象にはならない。
  - ただし「使用されたカードの効果を無効にする」等、使用中カードを直接参照する効果は `in_use` のカードに作用できる (例: バタフライジャマーのような効果無効化)。
  - 実装済み: `EffectFilterTag` に `"suppress_used_card"` を追加。`getEffectFilterBlockReason()` で `suppress_used_card` タグがあれば `in_use` ゾーンでもブロックしない。

## マジックの空撃ち

- 効果適用の対象がいなくても、コストを支払いカードをトラッシュに送るだけの「空撃ち」が可能。
- メイン/フラッシュ効果の使用タイミングは空撃ちでも通常通り。

(「空撃ち」の網羅的ルールは [03b_resolution-and-interrupts.md](./03b_resolution-and-interrupts.md) の「空撃ち」セクション参照)
