# Custom Orica Mechanics

この章は、公式バトルスピリッツには存在しないが、このプロジェクトでは扱う独自カード/独自裁定をまとめる。

前提:

- ルールの土台は公式バトルスピリッツのまま維持する。
- ただし、公式に存在しないギミックについては、ユーザー管理のサイトを一次ソースとして扱う。
- あいまいな点は、推測で埋めずにユーザーへ確認する。

## カスタムソースの優先順

1. サイト上の Q&A / 裁定
2. サイト上のカードテキスト
3. サイト上の errata / 更新履歴
4. ユーザーの口頭/チャット確認

補足:

- このサイトでは、errata 情報は基本的にカード本文へ反映済みの前提で読む。
- そのため、まず `Q&A / 裁定` と現在の `カード本文` を優先する。
- `errata` は主に更新履歴と変更理由の確認に使う。
- Q&A はカード本文だけで読み切れない処理順や対象条件を補う。
- サイト上の記述だけでは定義が閉じない場合は、ユーザー確認を暫定の authoritative clarification として採用し、`source-map` / `open-questions` / 該当章へ同ターンで反映する。

## 「このカード/ネクサス」併記の適用範囲

- **裁定 2026-08-07（ユーザー確認、信頼度 C）**: BSSA01-XX01 の「このカード/ネクサスの
  シンボル/軽減シンボルは紫/白/黄としても扱う」は、フィールドではネクサス、フィールド外では
  カードとして発揮する。したがって、配置後の実効シンボルだけでなく、手札から配置するときの
  軽減シンボル要求枠と、デッキ/手札/トラッシュ/手元/除外などにある表向きカードの実効シンボルも
  神に加えて紫/白/黄として扱う。裏向きカードは素性を持たないため対象外。
- カード本文のローカル一次資料: `external-qa/cardData.js` BSSA01-XX01 (`id:267`,
  `cardNumber:'BSSA01-XX01'`)。本文だけでは「このカード」がどの場外ゾーンまでを含むか閉じないため、
  上記ユーザー確認で補完した。
- 実装: `treat_as.appliesToCard:true` を自己カードのゾーン横断適用フラグとし、`symbol` は
  `getEffectiveSymbolBundles()`、`reduction_symbol` は `getEffectiveReductionSymbolEntries()` で解決する。

## 公式ルール側で確認でき、独自サイトでも再利用される概念

### 1. 魂状態

確認できたこと:

- `魂状態` は独自サイト専用の語ではなく、`batspi.com` の公式Q&Aでも説明されている。
- Q27442 では、
  - `「魂状態」にできるルールや効果で、フィールドに置かれた契約カード`
  - `この状態ではスピリットなどではない`
  - `上にコアを置く / アタックする / ブロックする / そのシンボルで軽減する`
    ができない
  - `Lv のある効果は発揮できない`
  - ただし `〖魂状態〗` と書かれた効果は Lv に関係なく発揮する
  という趣旨が示されている。

実装含意:

- `魂状態` は custom mechanic ではなく、公式側の `state / mode` の先例として扱う。
- 独自カードで似た「場にあるが通常のスピリット/ネクサスとしては扱わない状態」を作るときの参考モデルになる。

## 確認できた独自ギミック

### 1. 導界者ネクサス / 導シンボル

確認できたこと:

- `系統:「導界者」` を持つネクサスが存在する。
- 基本的には創界神ネクサスに近いが、完全に同一ではない。
- 導界者ネクサスは、創界神ネクサス対象の破壊/コア移動系の効果を受ける。
- 一方で、`創界神ネクサスがあるとき` のような条件では創界神ネクサスとして数えない。
- 出典（信頼度A）: `external-qa/qaData.js` `qa-002`（『導界者ネクサスは創界神ネクサスとどう違うの？』）に逐語で
  「このネクサス/スピリット/アルティメットは導界者ネクサス/創界神ネクサス対象の効果しか受けない。（中略）
  これにより、導界者ネクサスは、『創界神ネクサス1つを破壊する』／『創界神ネクサス1つのコアすべてをボイドに置く』／
  『創界神ネクサスのコア1個をこのスピリットに置く』などの効果を受けますが、『創界神ネクサスにコア+1する』などの
  効果でコアを置けず、『創界神ネクサスがあるとき』などの効果で創界神ネクサスとして数えられません。」とある。
- **原則の一般化（裁定 2026-08-02, ユーザー確認, P3-134）**: 「破壊/コア移動系」は例示であり
  網羅列挙ではない。本質は **「作用系（対象に何かを行う効果＝受ける）」と「存在/カウント条件
  （数えない）」の二分**。コスト変更・シンボル変更・免疫付与など、対象に作用する効果は
  種別を問わずすべて「受ける」側に属し、導界者ネクサスも対象に含める。カード文が
  「創界神ネクサス」とだけ書いていて「導界者ネクサス」と併記していなくても、それ自体は
  除外の根拠にならない（除外が正当なのは `field_has`/`field_lacks` 等の存在/カウント条件
  のみ）。詳細・発覚経緯は `issues/archive/P3-134/index.md`。
- `真・導託 / 導託 / 導域 / 転者` は、それぞれ `真・神託 / 神託 / 神域 / 転神` と対応づけて扱う前提がある。
- 導シンボルは神シンボルとは別物（色ではなく特殊シンボル種別）。
- **別軸の裁定（混同注意）: 単に「ネクサス」とだけ書かれた作用系効果（「創界神ネクサス」
  「導界者ネクサス」と明記しない）は、創界神/導界者ネクサスを対象に含めない（デフォルト除外）**。
  上記 qa-002 原文の前段「このネクサス/スピリット/アルティメットは**導界者ネクサス/創界神
  ネクサス対象の効果しか受けない**」は、創界神/導界者ネクサス自身が「創界神ネクサス」
  「導界者ネクサス」と明記された効果**しか**受けないという制約規定であり、裏を返せば
  無印の「ネクサス」効果は対象外という原則を定めている。P3-134 の一般化（「作用系は受ける」）
  は "`創界神ネクサス`と明記された効果に導界者ネクサスを含めるか" という**別の論点**（明記表記の
  対象範囲）であり、"無印「ネクサス」に創界神/導界者ネクサスを含めるか"（本項）とは軸が異なる。
  ただし「ネクサス」の参照には含む（[Q1532](08d_grandwalker-nexus.md)）。
  - precedent: `packages/card-data/src/cards/BSTH02.ts` BSTH02-C21「相手のネクサス」
    （創界神と明記しない）→ `category:["nexus"]` のみで `targetsGrandwalker` 省略
    （`matchesCardFilter` の既定除外により通常ネクサスのみが対象）。同カード内の
    「創界神ネクサス」明記部分は別 branch で `targetsGrandwalker:"only"` を明示指定。
  - SSOT: `packages/rules-core/src/dsl-types.ts` `CardFilter.targetsGrandwalker` コメント
    「省略 → 創界神/導界者ネクサスを対象から除外（デフォルト: 通常効果では対象外）」
    および `packages/rules-core/src/card/card-filter.ts:481-489`
    （`!filter.targetsGrandwalker && ... isGrandwalkerOrGuidedNexus(def) → return false`）。

実装含意:

- `nexus` の亜種として subtype/keyword で持つだけでは足りず、
  - 対象判定
  - コア配置/移動制限
  - シンボル判定
  を分けて扱う必要がある。
- **実装済み（P2-07 Phase F-3）**:
  - `CardFilter.field_has` / `field_lacks` に `grandwalkerKind: "grandwalker" | "guided" | "any"` 条件分離（`model.ts:1719-1720`）
  - 導シンボル: `SpecialSymbol: "guide"` ＝ 神シンボル `"god"` と並ぶ別種別。`SymbolColor = CardColor | SpecialSymbol` に含まれる（`model.ts:67-75`）
  - 導技ラベル: `DivineSkillData.label = "guided_skill"`（神技 `"divine_skill"` ／界放 `"divine_release"` ／契約 `"contract_skill"` と同列、`model.ts:980`）
  - keywordTag `"guided_nexus"` の命名規約は確定済み

### 2. スタック

確認できたこと（細則の正源は `20_design/08_stack-window-and-priority-loop.md`）:

- `スタック` はフラッシュに次ぐ**新しい発揮タイミング**。能動窓ではなく相手の行動への割り込みが基本。明示なき限り `flash`⇄`stack` は相互に発揮/使用不可。
- 割り込み対象（指定なき場合）: 相手の 召喚/配置/使用・常時以外の効果発揮/使用・アタック/ブロック宣言・バースト発動（独自Q&Aでは相手のスタック効果も対象）。
- 発生しない: コスト支払い自体・通常のライフ減少・効果不使用の基本ステップ処理・効果によらないコア移動。コスト未払いの宣言は支払い完了後の成立直前にスタック宣言。
- `アタック/ブロック宣言` へのスタックは宣言**未成立**のまま割り込む → 解決後に対象消失/行動不可ならキャンセル。条件付き効果も解決後に Lv 等を満たさなければ不発。※公式の宣言後フラッシュに入った後は成立済み宣言は取り消されない（custom スタックとの差）。
- バースト発動は発動宣言時/発揮宣言時の両方で発生しうるが、実際にスタックできるのは**片方のみ**。
- **常時効果そのもの**はスタック元にならない。`〜したとき` 型や開始タイミング（「このバトルの間」等）を持つ継続効果はスタック対象になりうるが、開始タイミングが補われないアタック中継続効果・`離れない` 等の常時効果はスタックしない（`qa-009`）。任意効果の不使用・`〜から〜まで` の開始点・シンボル固定の継続開始も原則スタックしない。
- 解決中の即時効果が内包する 召喚/配置/使用/発揮 には**追加のスタック窓を連鎖させない**（外側発揮にのみスタック）。ただし常時効果が通常行動（例: アタックステップに手札1枚召喚可）を許可しているだけなら、その宣言は通常宣言として扱いコスト支払い後の成立直前に通常どおりスタックが発生。

実装含意:

- これは単なる keyword ではなく、**公式 `flash` と別の timing layer**。
- battle 外へ広げるときも、official `flash` 側の基準はまず「ターンプレイヤーがメインステップ中に行う `flash` 行動」であり、相手に通常の `flash` 窓を配るものとしては扱わない。
- **実装済み**: `main_step_stack` / `pre_declaration_stack` / `stack_before_block` / `stack_after_block` 窓で timing layer 統合済み。詳細は `20_design/08_stack-window-and-priority-loop.md` 参照。
- 1-pass cascade モデル採用（2026-04-12 実装完了）: 片方パスで窓即クローズ、保留スタックは LIFO 一括解決。
- `PreDeclarationStackWindow` (attack / block / forced_block) で宣言前 tentative 保持 → stack 解決後に legality 再チェック。
- 解決中の即時効果が内包する `召喚 / 配置 / 使用 / 発揮` では、親効果から独立した第2のスタック窓を開かない（`qa-010` 対応）。
- 常時効果が timing window に通常行動を許可しているケースは、その宣言自体に通常どおりスタックが発生。

### 3. 黒 / 七色

確認できたこと:

- `黒` という追加属性/色が存在する。
- `黒` は空間・時間・次元・闇モチーフとして説明されている。
- `【装甲：∞】` は、相手フィールドに黒シンボルがあれば黒の効果も防ぐ。
- `六色` と `七色` は同一ではない。
- ただし、七色は `六色以上` には含まれる。

実装含意:

- `CardColor` 型に `"black"` を追加済み（`model.ts` / `cost-system.ts` 対応済み）。
- `七色` は `"black"` 追加により自動対応（`CARD_COLORS` に追従）。
- `exactly six` と `at least six` を分ける比較関数を実装済み:
  - `countUniqueColors(colors)`: 重複なし色数を返す
  - `matchesColorCount(colors, min?, max?)`: 色数条件判定（min のみ = N色以上、min=max = ちょうどN色）
  - `ConditionClause` に `self_color_count` 追加（自身の色数条件）
  - `EffectTarget` に `minColorCount` / `maxColorCount` 追加（対象フィルタ）

### 4. クォーツ

[入れ替え・ENIGMA再確認](07g_quartz-replacement.md)。

裁定確定（ソース: 独自サイト Q&A = precedence 最上位 / 信頼度 A。`external-qa/qaData.js` qa-029〜035, 2026-03-14。qa-039, 2026-08-10）:

- `クォーツ` は、メインステップに指定コストを払って対象へセットするギミック。最も近いのはミラージュ（手札からのみセット可、手元不可、既セット位置は入れ替え、効果でもセット可、クォーツ対象効果しか受けない、効果以外ではメインステップ以外セット不可）。
- **相違点**: セット先は別カード側の `このカードには…クォーツをセットできる` 記述で決まり、その効果を発揮できる状態のときのみセット可。**コストを払える限りメインステップ中に何度でもセット可**。セット先カードは通常効果の対象にでき、移動するとクォーツも同じ場所へ移動し**セット中ではなくなる**。
- **セットコスト** `C2` はカウントを消費（C2 = カウント -2。カウントが足りなければセット不可）。効果でセットする場合も「コストを支払わずに」表記が無ければクォーツコストは必須（qa-035）。
- **クォーツコストは効果ではない支払いコスト**。BSGE01-C13 等の「追加したカウントは自分の系統:『神喰』を持たない効果で数えられず、その効果を受けない」で保護されたカウントでも、クォーツコストの支払いには使用できる（qa-039）。
- **属性値** `<時>5` 等は色（黒/赤…）とは別軸。種類は 地/火/水/風/時/空/幻 の7種（qa-033）。host の【アーツ】解放条件をセット中クォーツの属性値合計で満たすためのもの。
- **スロット上限は host カードが定義**（一般則ではない）。例 `ENIGMA[戦術オーブメント]` = 左右3枚ずつ＋中央(下)1枚の **合計7枚まで**。かつ **同名クォーツは2枚以上セット不可**（qa-029）。
- host `ENIGMA[戦術オーブメント]` は「このカードにセット中のカードの【クォーツ】すべてを得て発揮する」を持ち、セット中クォーツ効果を自身の効果として発揮する（【セット中】表記の無いクォーツ効果はこの host 経由でのみ発揮。qa-030）。ENIGMA へのセットは**魂状態を対象とした効果である必要**がある。
- ENIGMA は Lv/BP 表記が無く、**BP0 ではなく BP が存在しない** → カード状態でも BP 参照効果の対象にできない（qa-031）。ENIGMA の【セット条件】は【合体条件】として**扱わない**（qa-032）。

実装含意:

- 単純な `attachedToInstanceId` では不足。set host / slot（左右3+中央1=7、同名不可）/ set cost（カウント消費）/ 属性値（7種・合計集計）/ host が得る効果 / host 移動時の追従（移動でセット解除）を持つ専用モデルが必要。
- `levelDefs` 空は BP 不在（BP0 と区別）。

## 実装ポリシー

- まずは公式バトスピ engine を壊さない。
- custom mechanic は extension layer として追加する。
- 追加順は次を基本にする。

1. source precedence と errata 反映を先に固める
2. enum / subtype / symbol 拡張で済むものを先に入れる
3. timing layer 追加が必要な `stack` を battle 以後で入れる
4. host-subcard 系: 専用モデルは `quartz` のみ（魂状態セット・§4）。`星霊衣` / `アルドノアドライブ` 等の「カードの下」は汎用アンダーカード基盤＋役割タグで扱う（[07b §6](07b_card-observed-mechanics.md) アンダーカード一般則、裁定 2026-06-11）
