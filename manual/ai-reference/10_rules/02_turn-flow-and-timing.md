# Turn Flow And Timing

## ターンの大枠

追加による割り込みと復帰は [02d 追加ステップ・追加ターン](02d_extra-steps-and-turns.md) を参照。追加ステップの終了後は挿入前の続きへ戻る。

次の順でターンを進める。

1. Start Step
2. Core Step
3. Draw Step
4. Refresh Step
5. Main Step
6. Attack Step
7. End Step

実装メモ:

- 各ステップは共通で `step_start` / `step_end` の窓を持つ。
  - `step_start`: ステップに入った直後。「〜ステップ開始時」効果をここで誘発・解決する。
  - `step_end`: ステップ固有の処理がすべて終わった後、まだそのステップ内にいる状態。「〜ステップ終了時」効果をここで誘発・解決し、すべて終わってから次のステップに遷移する。
- ステップ固有の処理（コア獲得、ドロー等）は `step_start` と `step_end` の間に行う。
- 効果窓全体ではなく内部サブ効果だけをステップ単位で gate する場合は `ConditionClause.step_phase`（`step` + `whose`）を使う。効果窓そのもののステップ限定は `TimingScope.period`。

補強根拠: `ルールQ&A` 目次スニペット / `ギャラクシーステップ`
（アタック後にコア→ドロー→リフレッシュ→メイン→アタックを再実行）。

## ゲーム開始手順 (Ver.17.0 改定)

1. 各プレイヤーのデッキ（40枚以上）をシャッフルする。
2. ボイドからコア5個をライフに置く。
3. ボイドからコア4個をリザーブに置く（**ソウルコア1個+通常コア3個で固定**）。
4. デッキの上から4枚を手札に加える。
5. じゃんけんで先攻/後攻を決定する（勝者が先攻）。
6. 手札が気に入らなければマリガン可能（手札をデッキに戻してシャッフルし、再度4枚引く。1回のみ）。
7. 先攻プレイヤーのスタートステップから開始する。

Ver.17.0 改定により:

- 手順3: ソウルコア使用が強制化（選択肢削除）。
- 手順5-6: マリガンタイミングが「ドロー後・じゃんけん前」から「先攻/後攻決定後」に変更。

- 契約カード使用時はドロー枚数・手順が変わる。詳細は `08a2_contract.md` を参照。

実装メモ:

- `initializeGame()` 関数として実装する。
- 各プレイヤーのボイドの初期コア数 = 200。実際にはライフ+リザーブ分を引いた残りがボイドに残る。
- 先攻の1ターン目はアタックステップをスキップする（アタック不可）。

## 先攻1ターン目の制限

- 先攻プレイヤーの最初のターンではアタックステップをスキップする（アタック不可）。
- 先攻プレイヤーの最初のターンではコアステップをスキップする（コアブーストなし）。
- ドローステップのドローは行う（先攻・後攻とも同じ）。

実装メモ:

- `turnNumber === 1` かつ先攻プレイヤーのとき、アタックステップ自体をスキップする（ステップに入らない）。
- `turnNumber === 1` かつ先攻プレイヤーのとき、コアステップ自体をスキップする（ステップに入らない）。

## Start Step

- 自分のスタートステップ時にデッキが 0 枚なら敗北。

実装メモ:

- ここで `checkLoseByDeckOut()` を行う。
- ターン開始時誘発はこの直後に積む。（実装済み: `advanceStep()` が `start_step` の `PendingTriggeredEffect` を自動キュー。デッキアウト時はキューしない。）

## Core Step

- ボイドからコア 1 個を自分のリザーブへ置く。

実装メモ:

- コア獲得は固定処理。ステップ送りは UI/AI の選択肢。
- 置換効果に備えて、内部的にはイベント化しておく。

## Draw Step

- 手札上限はない。
- ドローしようとしてデッキが 0 枚でも、その時点では敗北しない。
- ドローできないままターンを進め、次の自分のスタートステップで敗北判定する。

実装メモ:

- `draw(1)` は失敗してもゲーム続行。
- 失敗フラグではなく、デッキ枚数を次のスタートステップで参照するだけで足りる。

### 起動型「〜することで、1枚ドロー」の山札 0 枚判定（信頼度 A の公式 Q&A を適用）

- **逐語根拠**: 公式 Q22385 は「自分のデッキが0枚のときに、このネクサスのLv2効果を発揮することはできる？」に「**いいえ、できません。ドローすることができないため、自分の手札を破棄することもできません。**」と回答する（`external-qa-official/BS16.md:745-748`）。Q2247 も同じく「**ドローすることができないため、オープンすることもできません。**」とする（`external-qa-official/BS06.md:302-305`）。
- 上記はドローステップの「ドローできなくても直ちに敗北しない」とは別の、能動的に発揮する効果の可否である。したがって、本文が「Aすることで、1枚ドローする」だけの起動型効果は、山札 0 枚では A だけを実行して発揮することはできない。これは Q22385 の同型構文からの適用であり、Q27333（【オンステージ】限定）を一般則としては使わない。
- 実装: `BSTH001-C04` と `BSTH001-R01` は `field_has(zone:"deck", minCount:1)` を availability condition に置く。宣言前に候補外とすることで、`conditional_cost` の rollback による同一 no-op 宣言の反復も防ぐ。

### コスト先払い型ドロー枚数修正（裁定 2026-06-15, 信頼度 C / ユーザー確認）

「[任意コスト]を支払えば、このドローステップのドロー枚数を +N する」型（例: BSSL01-C03 カルテノン神殿 Lv2『自分のドローステップ』〔重複不可〕「手札の系統:「影」/「プレイヤー」カード1枚を破棄することで、ドロー枚数を+1する」）の確定モデル:

- **プレ判断モデル（A）が忠実**: システムドロー前に任意コストを判断し、支払えた場合のみ +N を確定する。順序は **コスト → ボーナス確定 → システムドロー**。ドローステップを中断・再開できる必要がある。
- **ポスト等価モデル（B）は不可**: 「基本ドロー → discard → 追加ドロー」は本文順序を逆転させ、「ドローステップで引いた総枚数」参照にも基本枚数を誤提示する。
- **対比（無条件 draw_modify）**: BSTH01-C12 はシステムドロー前に +2 を確定し、discard は強制・ドロー後。任意コスト前提型とは別経路。〔重複不可〕は同名間の重複抑止のみ。

## Refresh Step

- 疲労状態のスピリットを回復状態へ戻す。
- 重疲労状態のスピリットは疲労状態に戻る（一段階回復）。回復状態にはならない。
- 自分のトラッシュにあるコアをすべてリザーブへ戻す。

実装メモ:

- カード本体のトラッシュとコアのトラッシュは分離管理する。
- 疲労状態は `ExhaustState = "recovered" | "exhausted" | "heavily_exhausted"` で管理し、リフレッシュステップでは `recover` 行為（1段階戻す）を適用する。
- 効果の「回復する／回復させる」も一段階だけ戻す。「回復状態にする」は重疲労から直接回復状態にする。DSL は前者を `recover`、後者を `set_exhaust_state(state:"recovered")` で区別する（2026-09-23 ユーザー確認・信頼度B。通常回復の裏付け: 公式ミラー `external-qa-official/BS45.md` Q27141）。
- 「回復できない」は一段階回復を禁止し、「回復状態にする」は禁止しない。「回復状態にできない」は重疲労→疲労を許可し、疲労→回復と「回復状態にする」を禁止する。`restrict_recovery.restriction` は前者が `recover`（既定）、後者が `become_recovered`（2026-09-23 ユーザー確認・信頼度B）。次回リフレッシュの「回復できない」も重疲労→疲労を禁止し、そのリフレッシュで期限切れとなる。

## Main Step

- 召喚、配置、コア移動、マジックのメイン使用の主戦場。
- メインステップでは、ターンプレイヤーが `flash` タイミングの効果やカード使用を行える。
- これはアタックステップ中の前半/後半フラッシュのような双方共有の割り込み窓ではなく、まずターンプレイヤー側の通常行動として扱う。
- フィールドのカード上のコアは、召喚・配置・使用などのコスト支払いに使える。基本的にコアを置く通常操作はメインステップ中に行う。

実装メモ: `MoveCoreAction`/`SummonAction`（スピリット/アルティメット/ブレイヴ）/`DeployNexusAction`/
`UseMagicAction`/`BraveAttach/Swap/SeparateAction`を許可
（宣言タイミング窓一般原則は[02b](02b_declaration-timing-window-principle.md)）。

- 手動コア移動は `core-draft`/`core-move` batch。学習は `manual_core_move` で露出

## Attack Step

- アタックは 1 体ずつ順番に行い、1 件ずつ解決する。
- アタック/ブロック宣言後に当該スピリットは疲労する。
- アタック時効果はアタック宣言で疲労した後に発揮する。
- アタック時とアタックによる疲労時は同時誘発。解決中のLv上昇でLv条件付き効果を発揮できる（公式Q30857、A / 採用）。[観測範囲・群完了との境界](02e_simultaneous-trigger-eligibility.md)を参照。
- 通常アタックでは持続しない `アタック時` 効果を解決してからブロック宣言へ進む。
- 指定アタックでも、まず `アタック時` 効果とアタック宣言起因のバースト/待機誘発を片付け、その後 still-valid なら強制ブロック宣言へ進む。
- したがって、指定アタックの `ブロック時` 効果は、`アタック時` 効果と同時発揮グループに混ぜるより、強制ブロック宣言の時点で block-side 即時効果として積む前提で扱う。
- いったんアタック / ブロック宣言が成立して通常フラッシュに入った後は、そのスピリットがいなくなったり行動不能になっても、成立済みのアタック / ブロック自体は取り消されない。
- 通常のフラッシュタイミングは
  - アタック宣言後
  - ブロック宣言後
    の 2 回。
- ブロック宣言がなかった場合、後半のフラッシュはなく、そのままバトル解決に入る。
- アタックステップ中に 1 度もアタックしなくてもよい。
- ただし、アタックステップ開始時の効果がある場合は、それを無視して即終了はできない。

実装メモ:

- `AttackStep` の中にさらに小窓を切る（`step_start` / `step_end` は共通パターン）。
  - `step_start`（アタックステップ開始時）
  - `declare_attack`
  - `flash_before_block`
  - `declare_block`
  - `flash_after_block`
  - `battle_resolution`
  - `step_end`（アタックステップ終了時。まだアタックステップ内）

## End Step

- エンドステップ効果を解決し、その後 `removeExpiredContinuousEffects()` で `this_turn` 効果を除去してターン終了。
- `このターンの間` はエンドステップ開始で消えるのではなく、終了時効果の後に消える。
- 効果でターン終了する場合、効果解決後に派生/待機効果をすべて解決してから一時効果を無効化して終了する。エンドステップ自体は行わず『エンドステップ』効果は解決不可（公式 Q30302-Q30304, PB41-RV004）。
- 実際の終了時までに「ターンを終了できない」が成立した場合、終了は不成立となり、元のメイン/フラッシュ等を続ける（公式 Q17595, PC01-X01）。

## スタック窓 (Stack Timing)

独自拡張ルール。行動宣言に対して相手が割り込み (stack) できる応答期間。
設計詳細は `20_design/08_stack-window-and-priority-loop.md` を参照。

### 基本ルール

- 召喚/配置/使用、常時以外の効果発揮、アタック/ブロック宣言、バースト発動に対してスタック宣言が可能。
- **1つの行動に対して宣言できるスタック効果は1つだけ。片方がパスした時点でスタック窓は即閉じる。** (2026-03-31 ユーザー確認)
- コスト支払い完了後に窓が開く。
- スタック効果は応答元とは独立した効果であり、応答元による誘発効果ではない。後から宣言した順に、各効果の本文と、それによる誘発・転醒・離脱処理・効果発揮後・バーストとその誘発を完了してから次のスタック効果へ進む。スタック機会・解決順と、誘発の因果関係を混同しない（2026-09-26 ユーザー確認）。
- 通常の内側誘発から発動したバーストは、同じ原因効果に由来する外側の誘発も空になるまで効果発揮を待つ。例: スタックAへBで応答し、BからC・D、DからE、EからバーストFが生じた場合、B→D→E→F発動宣言→C→F発揮宣言・本体とその誘発→Aの順。独立したAを通常の外側誘発として待機対象に混ぜない（2026-09-26 ユーザー確認）。
- 解決中の即時効果が内包する召喚/配置/使用にはスタック窓が開かない。常時効果が timing window に通常行動を許可するケースでは通常どおり開く。内包召喚の維持コア配置も「解決中」に属する（2026-06-21 裁定。詳細は `20_design/08` §5 / issue P3-110）。
- 原文テキスト上で1つの効果に含まれる「Aするか、Bする」等の分岐は、効果発揮宣言を分岐別に分割しない。宣言は1回だけ行い、スタック窓が閉じて効果解決に入ってから分岐を選ぶ。分岐固有の対象選択・効果文内コストも、その分岐を選んだ後に処理する。DSL では同一 `EffectStep.choice` の各枝がこれに該当する（2026-08-13 ユーザー確認）。
- 原文テキスト上で別々の起動効果として記載された選択肢は、上記と異なり別々の発揮宣言として扱う。
- アタック/ブロック宣言はスタック解決まで未成立で保持し、解決後に legality を再チェック。不正ならキャンセル/不発。
- **フラッシュ効果 ≠ スタック効果（独自Q&A qa-005: スタック効果＝フラッシュ効果とは別の割り込み応答）。** スタックタイミングでは、スタック効果と、本文でその窓の使用を許可された行動を行える。後者にスタック見出しがなければスタック効果には分類しない（[03c 効果種別](03c_effect-text-interpretation.md)）。フラッシュ効果はフラッシュタイミング（優先権ループ／メイン）で使い、相手のフラッシュへの応答も本体ループで交互に使う。実装注記は `20_design/08` §4。

起動型キーワード、窓を開かない処理、バースト2段階窓、ただちに誘発、発揮前チェックポイントの詳細は [02b_declaration-timing-window-principle.md](02b_declaration-timing-window-principle.md) を参照。

窓後の必要コア不足（召喚不成立・トラッシュ）と宣言自体の違法化（宣言・支払いのみ取り消し）の区別は [03f](03f_stack-failure-and-waiting-cores.md) を参照。

## フラッシュタイミングの優先権ループ

アタックステップのフラッシュタイミングでは、両プレイヤーが交互にフラッシュ効果を使用/パスする優先権ループが走る。

- フラッシュは2回: アタック宣言後 (`flash_before_block`) とブロック宣言後 (`flash_after_block`)。
- ブロック宣言がなかった場合、後半フラッシュはない。
- 最初の優先権は非アクティブプレイヤー (ブロック側)。
- フラッシュ使用後はスタックサブ窓が開き、解決後にループ継続。2連続パスでフラッシュ窓が閉じる。
- **優先権の交互は「能動フラッシュ使用」でのみ進む。** 能動使用→解決で優先権は相手へ移譲。誘発効果 (例 BSTH01-X05 咲夜の発揮前無効化) は誘発レイヤーで交互を進めない。よって「自分フラッシュ使用→相手誘発で無効→**相手のフラッシュタイミング**」で、無効化した相手の誘発が能動使用のごとく優先権を使用者へ跳ね返してはならない（2026-06-21、`usePassBattleFlashAsAction` 最外 `triggered_effect` 分岐。回帰 `flash-priority-after-induced-negate.test.ts`）。

設計詳細は `20_design/08_stack-window-and-priority-loop.md` §4 を参照。
