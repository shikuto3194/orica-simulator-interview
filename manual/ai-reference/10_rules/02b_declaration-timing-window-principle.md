# 宣言アクションのタイミング窓一般原則

`02_turn-flow-and-timing.md` の Main Step / スタック窓節から分割（サイズ上限のため、2026-07-18 / 2026-08-13）。

## 一般原則（裁定 2026-07-18, 信頼度 B）

カードテキストに明示的なタイミング指定（「自分のメインステップに」等）が無いからといって、
「相手ターンの相手の任意の非窓ステップでも常に宣言可能」にはならない。

この engine で `getCurrentMagicActionTimings`（開いている main/flash/stack いずれかの窓）を
時系判定基盤に使う宣言アクション（`use_magic` / `declare_manifest` / `declare_advent` /
`use_divine_skill` / `link_aid` 等）は例外なく、(1) 何らかの使用可能窓が開いていること、
多くは加えて (2) `isActivePlayer`（自ターン）、の両方をゲートに持つ。
`getAvailableManifestLegalActions`（`legal-actions-availability.ts:8424-8435`）が代表例で、
`timings.length === 0` で早期 return した上でさらに `isActivePlayer` を検査する二段ゲート。

「フィールドに置く」系の効果もこの原則の対象になる。カード本文が「条件を満たしている間、
フィールドに置き」としか書いておらず、明示的なタイミング語彙もスタック窓の有無への言及も
無い場合、以下のいずれかで裁定する必要があり、**ゲートを丸ごと撤廃して良い根拠にはならない**。

- 独自カードサイト Q&A に直接該当が無い場合は、`02_turn-flow-and-timing.md:190`
  「召喚/配置/使用...に対してスタック宣言が可能」のカテゴリ整合と、同ファイル Main Step
  「基本的にフィールドのカードへコアを置く通常操作はメインステップ中に行う」という既定
  慣行を優先し、ユーザー確認を仰ぐ。
- 「自ターンかどうか」と「窓（main/flash/stack）が開いているかどうか」は独立した2軸であり、
  片方だけをゲートにすると（自ターンの非窓ステップ全域で常時宣言可能、または相手ターンの
  窓中でも宣言可能、のように）他の同種アクションと非対称になる。新規アクション種別を追加
  する際は、既存の同型アクション（マジック的宣言なら `use_magic`/`declare_manifest` 系、
  「フィールドに置く」系なら `place_nexus`/`summon` 系）と窓構成を揃えるのが既定。

## 具体事例: BSLH01-T07〜T17【アーツ】自己配置

確定裁定（ユーザー確認 2026-07-18）により、原文の「属性値が以下を満たしている間、
フィールドに置き」は、発揮開始タイミング語彙を持たない継続処理である。したがって配置は
`place_arts_token` の LegalAction ではなく、条件を満たした安定状態でトークンプールから
自動配置する state-based 処理である。誰のターンか、また main/flash/stack の窓が開いているかを
問わず、宣言・コスト・選択・スタック窓を伴わない。

- qa-016（`external-qa/qaData.js`）は「離れるとき」などの発揮タイミング指定がない効果を
  常時効果として扱い、スタックタイミング元にしない。本文に同様の発揮開始語彙がない本件も
  この判定に従う。qa-033 はこのトークンを「トークンマジック」と明記するが、配置を任意に
  宣言するとは述べない。
- 条件を失った既存トークンは同じ継続監視の反対側として
  `vanish_due_to_arts_gate_lost` で離脱する。原文の「使用できる」側だけは可能形の任意処理であり、
  アタックステップの通常のマジック使用宣言経路に従う。
- コード内コメントが「qa-035（原文に「自分のメインステップに」と明記）」を根拠として
  引用していた箇所は事実誤認: 実際の qa-035（`qaData.js` id=qa-035）は
  BSLH01-R01「クォーツコストは支払うか」という別質問であり、メインステップ限定とは無関係。

## セット/魂状態化アクションと効果文内処理

`set_mirage` / `set_quartz` / `activate_soul_state` は、プレイヤーがメインステップ中に
能動宣言する LegalAction 経路では `02_turn-flow-and-timing.md` 02:188-190 の対象として
コスト支払い後にスタック窓を開く。

一方、効果文の解決中に `set_mirage` / `quartz_set` / `enter_soul_state` 相当の状態遷移が
発生する場合は、同ファイル 02:191「解決中の即時効果が内包する召喚/配置/使用には
スタック窓が開かない」に従い、その外側の効果発揮宣言だけが応答対象になる。

## 起動型キーワード効果の発揮宣言と効果文内コスト

神技/導技/リンクエイド/契約合体/煌臨等の発揮宣言も「常時以外の効果発揮」で窓を開く。
効果文内の起動コスト（「○○することで」等）は**使用コストでなく効果文内＝窓後に消費**
（08c:196 一般化。実装例 `applyDivineSkillAction`）。カード固有裁定に窓の言及が無くても
「窓不要」ではない（P3-112）。

## スタック窓が開かない場合

- コスト支払い
- 通常のライフ減少
- 効果を使っていない基本ステップ処理
- 効果によらないコア移動
- 任意効果の不使用
- 常時効果そのもの

## バースト発動の2段階窓

バースト発動時は **発動宣言窓** と **効果発揮宣言窓** の2段階が開く。

- 発動宣言窓でサブスタックが使われた場合、効果発揮宣言窓は開かない（片方のみ）。
- 根拠:「バーストを破棄する」「バースト効果を無効にする」が専用対抗手段として存在するため、両方の窓が必要。

裁定根拠: `source-findings-custom.md` §2 (qa-005〜qa-016)

## 同時誘発の順序選択と応答窓

- 同時に待機した公開効果は、ターンプレイヤーが次に解決する効果を1つ選び、その効果の所有者が発揮するかを決める。相手ターンに自分の複数効果が誘発した場合も、相手の順序選択より先に発揮・辞退できない。同じイベントに複数カードや同一カードの複数効果が反応する場合も、選択単位は個々の効果である。
- 順序選択後は、選択された効果だけを発揮・辞退できる。発揮宣言した場合は、残りの同時誘発より先に相手のスタック応答を処理し、その効果を解決する。戦闘中の前半・後半フラッシュ内でも同じ。辞退した場合はその効果だけを取り除き、残りは保持する。
- BSGE01-TR01(A)の契約合体時効果の「カウント+2」と「その後、ただちに裏返せる」は一つの効果。裏返しの選択を含む解決が終わってから、カウント増加誘発とB面の転醒時効果を同時誘発として扱い、どちらから解決してもよい。

根拠: 2026-09-12 ユーザー確認（信頼度C）。発揮宣言への応答は [02 スタック窓](02_turn-flow-and-timing.md#スタック窓-stack-timing) の一般則。

### 派生した効果ツリーの解決順（2026-09-15 確認）

各誘発タイミングの境界と原因ID必須化は[02d](02d_trigger-timing-and-causality.md)（2026-09-25公式再確認）。

- 一つの効果の解決によって内側に派生誘発が生じた場合、その効果本文を解決し終えてから、内側をすべて解決する。内側が空になるまで、外側に残る同時誘発を選択・発揮・辞退できない。さらに派生した場合も同じ原則を再帰的に適用する。
- 順番を選べるのは現在の内側にある同時誘発群の中だけ。「ただちに」の優先もその群の中で適用し、外側を先に解決する根拠にはしない。
- 例: BSTS01-C01の煌臨時と、CX01の「煌臨したとき」が同時誘発。CX01のカウント+1を先に解決したら、そこから誘発するCX01のドローを解決または辞退してから、C01の煌臨時へ戻る。キューの前面化もこの順番を越えられない（ユーザー提示スナップショット 2026-09-14T14:58:17.840Z）。
- 根拠A（実装に適用）: [公式エターナルQ6645](https://www.battlespirits.com/faq/list.php?format=eternal&prodname=BS41) は派生した召喚時について「『このスピリットの召喚時』効果が必ず先に解決されます。」と回答。[Q6163](https://www.battlespirits.com/faq/list.php?format=eternal&prodname=BS38) も一つ目のアクセルとその派生を解決してから二つ目へ進む。逐語ミラー: `external-qa-official/BS41.md` / `BS38.md`。一般原則と上記の独自カード例は2026-09-15ユーザー確認Cでも一致。
- 実装: `trigger-resolution-scope.ts` が原因チェーンと同時誘発群から現在の内側を求め、合法手・操作権・公開誘発の実行ガードで共用する。外側の待機状態自体は保持する。

## ただちに誘発

「ただちに」誘発は割り込まず、原因処理後の同時誘発群で通常より先。通常解決開始後はタイミングを失う。根拠: `CB28/CB26/CB34/SD51`。実装: `triggerPriority:"immediate"`。

2026-09-26ユーザー確認（C、実装採用）: BSAZ02-C03の召喚時は、同じ召喚から生じるC10/X04の「ただちに」下置きを先に解決し、その後で下カードの存在条件を判定する。先行処理前の条件未達だけで通常候補を消さない。下置きを辞退・不成立とした場合は通常群へ戻る時点で除去し、後の通常効果による条件成立で復活させない。既に発揮場所を失った候補の除去と、宣言済み効果の不発は従来どおり。根拠の区分は[調査記録](../00_meta/source-findings-aldnoah.md)。

## 発揮前に無効化する誘発とスタック窓の順序

「相手が〜を使用したとき、その効果発揮前に無効にする」型の誘発（例 BSTH01-X05 咲夜）は **誘発効果でありスタック効果ではない**。よってスタックタイミング許可で gate されない（仮に「相手はスタックタイミングを行えない」効果があっても発揮できる）。誘発レイヤーと能動スタックレイヤーは別系統。

解決順序 (stack-first): 相手のフラッシュ使用に対する **スタック窓（能動応答）を先に処理** し、相手がパスして窓がクローズした後、対象（相手フラッシュ）の **発揮直前の「発揮前チェックポイント」** で当該誘発を発揮可否（declare/skip）解決する。これにより誘発はスタック窓と独立レイヤーのまま「発揮前」の無効化を成立させる。複数の同型誘発が同一使用イベントで誘発した場合、1 つが対象を無効化すると残りは「ことで構文」の双方向則（`03c` ことで構文 / `03b` 空撃ち節）により対象不在で発揮宣言できない（不発）。

裁定根拠: 2026-06-08 ユーザー確認（案X）。実装メモは `20_design/08_stack-window-and-priority-loop.md` §5。
