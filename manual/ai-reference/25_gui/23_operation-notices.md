# 日次の運営通知

ホームの既存「運営通知」から一覧・詳細へ進む。レイアウトと文字装飾は
メッセージ画面の `message-inbox` / `message-header` / `invitation-detail` を共有する。
見出しは明朝・金色・500、本文は既存の14px。独自テーマは追加しない。
メッセージ・運営通知の各通知ブロックは既存パネル色と24pxの背景ブラーを使う。
画面背景全体や招待先選択の項目は変更しない。

## 掲載と既読

- 日本時間0時に前日分を生成。通知は1日1件、変更なしは作らない。
- 最新10件を保持し、11件目の掲載と同じトランザクションで最古を削除する。
  日数による期限はない。削除された通知の既読も外部キーで削除する。
- 一覧は日付の降順。運営通知を開いて一覧を取得した時点で、本人の未読分をまとめて既読にする。
  詳細を個別に開く必要はない。ホームには未読件数を表示し、ホームの取得だけでは既読にしない。
- ホーム・一覧は30秒ごと（表示中のみ）とフォーカス復帰時に再取得する。
  運営通知の表示中に取得した新着も既読にする。取得失敗は再試行可能。
  既読失敗は一覧・本文を表示したまま理由を表示し、未読を維持する。「更新」で再試行できる。
- ログイン済み利用者は通知を読むことと本人の既読追加だけができる。
  生成状態と掲載RPCはservice_role専用。アプリの対戦APIが停止していてもDBから読める。

## 生成処理

`scripts/notices/run-digest.mjs` がフロントの `release-version.json` と対戦APIの
`/healthz` を確認し、両方に含まれるmainの共通リビジョンまでを対象にする。
GitHub activity API（2022-11-28）の `timestamp`・前後SHAで前日終了前のmain反映を特定し、
前回の処理済みリビジョンとの差分を読む。コミット作成日時では集計しない。
活動履歴は必要な境界までページ取得し、現在のmain・履歴の連続性を検査する。
同一活動の重複は除外し、欠落・強制更新・取得失敗は掲載を保留する。
枝の古いコミットはmainへの統合日で扱う。公開反映が遅れた変更は次回へ繰り越す。
初回はDB導入前日の開始前のmainを基点とし、それ以前を遡って大量掲載しない。
初回が失敗した場合も、DBに保存した開始日は動かさず未掲載分を保持する。
前日末以降の変更がどちらかの公開版へ含まれる場合、取消済みの修正を告知しないよう、
未掲載分全体を翌日へ繰り越す。生成中の公開版変更も再試行する。
境界後が運用・文書等だけで、告知候補の公開ファイルに最終差分がない場合は、
対象リビジョンを前日末までに制限して生成する。

コミット文と最終差分から利用者向けの項目を生成し、同じ機能・カードをまとめる。
テスト・文書・監査・CIだけの変更を除外し、内部リファクタのみの変更は理由付きで省略する。
画面・対戦エンジン・カード定義に加えて、SQL migrationと公開素材も候補に含める。
SQLを含む場合はservice_role専用 `operation_notice_migrations_applied` で適用履歴を
生成前・掲載前に確認する。未適用・履歴未登録のSQLは「変更なし」にせず保留する。
各項目の出典コミット・ファイル・差分の逐語抜粋と全コミットの扱いを検証する。
カードファイルは構文解析し、変更カードの名前・本文・効果を含む定義全体の変更前後を
`cardContexts` に渡す。資料は評価実行せず、上限を超えた場合は省略せず停止する。
校閲は本文を主張ごとに分け、対象・タイミング・処理・条件・変更前後と出典引用を記録する。
全本文を覆う照合と見出し・導入の承認が必要で、`approved` と理由だけでは掲載しない。
引用の存在確認と意味の妥当性は別であり、後者は独立校閲が周辺処理まで照合する。
別の校閲で誇張・推測・重複・主要変更の欠落を確認する。生成・校閲・公開版確認が
失敗したら掲載も処理済みカーソル更新も行わない。差分を切り捨てて要約しない。
掲載直前にも公開版を再確認する。

生成・独立校閲の資料は、完全なevidenceと校閲対象summaryを標準入力で渡す。
ツール出力の省略や長いJSONの反復読取を避け、モデルには資料外の調査・ツール実行を禁じる。
保存済み `evidence.json` と `summary-to-review.json` は同じ内容の監査用記録として残す。
資料内の命令は無視し、出典・全コミットの扱い・独立校閲の検査を維持する。
本文は画面・操作・効果で確認できる変化とし、内部の型・共有判定・参照先等の実装説明を避ける。
大きな差分の生成上限は18分、独立校閲は8分とし、合計26分に制限する。
既存タスクの30分制限は変更せず、履歴取得・公開確認・保存に4分の余裕を残す。
各工程の上限も診断へ記録し、超過時は掲載とカーソル更新を保留する。

生成物・診断は `artifacts/notices/<対象日>/`。認証キーは生成モデルへ渡さない。
生成・校閲の各 `*.diagnostic.json` は最新試行の終了状態・拒否分類・使用量を上限付きで保存する。
診断は固定のコマンド・エラー分類に限定し、任意の引数・ツール出力・資料本文・モデル本文・
アカウント識別子を保存しない。ポリシー拒否は権限拡大や別経路で回避しない。
`complete_operation_notice_digest` は生成状態を行ロックし、期待した日付・SHAとの一致を
検査して掲載・保持件数・カーソルを原子的に更新する。同日再実行や並行実行で重複しない。

## 運用と検証

main統合後、`scripts/notices/register-task.ps1 -Root C:\dev\orica-simulator` で
Windowsの `orica-daily-notices` を登録する。ユーザーのログインセッションで非表示実行し、
日本時間0時を基点に15分間隔で再試行する。掲載済みの日は生成処理を行わない。
PC停止・スリープ中は生成できない。起動後に前日分と未掲載の差分をまとめる。
ログイン時トリガーと `StartWhenAvailable` で再開する。GitHub CLIの当該リポジトリ読取認証が必要。
既定では実行ごとにデスクトップ版のbundled CLIを更新日時順に探し、存在する実体を使う。
登録時にversion directoryを固定しないため、アプリ更新後も新しいCLIを解決できる。
`-CodexExecutable` を明示した場合だけ、そのCLIの実体を固定する。
下書き生成は `gpt-6-luna` / `high`、独立校閲は従来どおり `gpt-6.1-sol` / `xhigh`。
各段階を最初から別ジョブとしてread-only・承認なしで実行し、途中のモデル切替や失敗時の上位モデル再生成は行わない。
既存の証拠照合・独立校閲・公開条件は維持する。選択モデルと推論設定は各段階の診断JSONへ記録する。
`--ignore-user-config` で通知編集に不要な外部MCPを起動せず、既存ChatGPT認証を使う。
Windows backendは子CLIに `windows.sandbox="elevated"` を明示し、user設定除外時も
read-only境界を実施する。global config・rules・trust・認証は変更しない。

- 単体・DB: `operation-notice-digest.test.ts` / `operation-notices-postgres.test.ts`。
- GUI: `e2e/operation-notices.spec.ts`。縦・横・デスクトップ、詳細・既読・再試行・はみ出し。
- メッセージのブラー: `e2e/room-invitations.spec.ts`。ホームと共通配色の回帰も実行する。

出典（2026-10-01確認、信頼度A、実装に採用）:
[Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security)
（SELECTとINSERTの権限、本人限定ポリシー）。

出典（2026-10-02確認、信頼度A、実装に採用）:
[GitHub repository activities](https://docs.github.com/en/rest/repos/repos#list-repository-activities)
（mainへの実反映履歴、cursor pagination。バージョンを固定し、実レスポンスでも確認）。

## 初回公開後の追補（2026-10-02）

ユーザーの依頼により初回公開後の変更を3件にまとめて掲載する。
日次生成の初回範囲とは別の一度限りの追補で、本文と出典・省略理由は
`scripts/notices/releases/20261002-backfill.json` に固定する。
対象は9月19〜23日、9月24〜27日、9月28日〜10月2日午前。
日付は各まとめの期間末日。実際の掲載日時は `published_at` に保持する。

初回公開タグ・GitHub Releaseはなく、Netlify初回配備SHAも未取得。
公開用dist分離 `f15cd07f3` と9月19日の公開サイト確認記録
（`00_meta/local-pc-deployment.md`）から境界を推定する（信頼度B）。
9月23日・27日末のmainはGitHub activityの実反映時刻から決める。
作成日時の古い枝も統合時の期間へ含め、公開済みの最終差分を校閲する。

既存テーブル形式で掲載し、既存RLS・権限・保持上限は変更しない。
掲載済みの同一3件は再挿入せず、通知とカーソルは同じトランザクションで更新する。
`scripts/notices/backfill-publication.mjs` が具体的な掲載SQLを生成する。
公開フロント・APIの両SHAと適用済みmigration、DBの直前状態を確認してから実行する。
通知と生成状態をロックし、期待したカーソルとの一致を検査して3件を原子的に掲載する。
同一本文の再実行は既読・掲載日時を保持し、部分掲載や本文不一致は停止する。

カーソルの `last_day` は追補③の通知日（10月2日）に合わせて日付を確保する。
`through_revision` は本文で説明した公開版 `7728ea61f` のままにする。
10月2日午前以降の未告知差分はカーソルのSHAから次の空いている日次へ繰り越す。
前日10月1日をカーソルにすると翌日の日次が10月2日の主キーへ衝突するため使用しない。
端末pushは送信しない。

## 公開済み通知の訂正

2026-10-03分の訂正原稿は `scripts/notices/releases/20261003-correction.json`。
隠岐奈の強制配置時神託という誤記と実装を任意へ戻し、BSAZ02の対象・処理、
BSSL01の煌臨元追加/トラッシュ選択、バトル解決時の説明を具体化する。
`buildNoticeCorrectionSql` は原稿からSQLを生成し、対象日の行をロックして
訂正前本文との一致を確認する。同一訂正の再実行は何も変更せず、不一致時は停止する。
日付・公開日時・既読・生成カーソルは保持する。実装変更を伴う訂正は公開フロントとAPIに
修正が含まれることを確認してから掲載する。本文に訂正日を明記する。
