### 2. スタック

- **2026-09-27再確認（B、ユーザー確定裁定）**: 「スタックタイミングはスタック元から派生する誘発効果ではなく、スタックタイミングという機会である」。BSTH04-X01導技にBSTH11-X01神技で応答し、手札へ戻した対象が導技解決時まで待機するのは誤り。
  独自ミラー`external-qa/qaData.js`のqa-005/qa-012（機会）とqa-049（窓後の対象選択）、両カード本文、および2026-09-26確認を照合した。実装にはBを適用し、[04の待機解除](../10_rules/04_state-based-rules.md#フラッシュのタイミング原則)へ反映。入力待ちの分類は`pending-resolution-policy.ts`、再開判定は`stack-resolution-core.ts`、回帰は`stack-response-leave-boundary.test.ts`。

- `スタックとは？` (`qa-005`) と `厳密にはどのタイミングでスタックを宣言するの？` (`qa-012`) から、
  - 相手の召喚/配置/使用
  - 常時以外の効果発揮
  - アタック/ブロック宣言
  - バースト発動
  などに対して割り込む独自 timing layer が存在する。
  - その対象には、相手の `スタック` 効果の発揮/使用も含まれる。
  - **1つの行動に対して宣言できるスタック効果は1つだけ。片方がパスした時点でスタック窓は即閉じる。** (2026-03-31 ユーザー確認)
  - 召喚/配置/使用や効果発揮で未払いコストがある場合、スタック宣言はコスト支払い完了後に行う。
  - バーストでは、表向きにした直後の発動宣言と、バースト効果の発揮宣言の両方でスタックが発生しうるが、実際にスタックできるのはどちらか片方のみ。
- `qa-007` `qa-009` `qa-016` から、
  - 常時効果そのものは stack timing 元にならない。
  - `〜したとき` のように効果文中に発揮タイミングが書かれているものは、見出しにタイミング名がなくても常時効果ではない。
  - `qa-009` では、`「このバトルの間」「このターンの間」など` を効果の発揮開始タイミングの例として挙げ、それが書かれていないアタック中継続効果は常時効果だとしている。
  - したがって、`『このスピリットのアタック時』このバトルの間、〜する` のような開始タイミングつき継続効果は stack 対象になりうるが、`『このスピリットのアタック時』〜する` のような開始タイミングなしのアタック中継続効果自体は stack しない。
  - `qa-016` でも、「離れるとき」などの指定を持たない `離れない` 効果は常時効果として扱い、stack timing 元にならない。
- 一方で、同じ Q&A から、
  - コスト支払い
  - 通常のライフ減少
  - 効果を使っていない基本ステップ処理
  - 効果によらないコア移動
  には原則発生しない。
- `「召喚する」効果には、その効果発揮宣言とそれによる召喚宣言で合計2回スタックタイミングが発生するの？」` (`qa-010`) から、
  - `召喚する` 効果では、外側の効果発揮宣言に対して 1 回だけスタックが発生する。
  - 効果文内で行う召喚宣言自体に、追加のスタックタイミングは発生しない。
  - 現行運用では、この構造を user-confirmed ruling として、**解決中の即時効果** が内包する `配置 / 使用 / 効果発揮` にも一般化し、内側行為ごとに追加 stack を開かない前提で扱う。
  - ただし、常時効果が timing window に通常の `召喚 / 配置 / 使用` を許可しているだけのケースは別で、その宣言自体に通常どおり stack が発生する。
- `qa-006` `qa-007` `qa-008` `qa-009` から、
  - 任意効果を使わないとき、その不使用自体にはスタックしない。
  - 明示タイミングを持たない `〜したとき` 型でも、常時効果でなければスタック対象になりうる。
  - `〜から〜まで` 型効果の `〜から` の開始点や、アタック時のシンボル固定のような継続効果開始には原則スタックしない。

### 4. クォーツ（確定 / 信頼度 A、qa-029〜035, qa-039）

- 2026-09-27、qa-029の「既にセットされている位置にセットするときは、セットされているカードと入れ替える」を再確認。通常・効果セット双方へ反映。出典別信頼度と本文照合は [07g](../10_rules/07g_quartz-replacement.md)。

- クォーツはメインステップに特別なセットコストを払って host にセットする（ミラージュに近いが別物）。
- `C2` のような count 系コストを持つ（C2 = カウント -2。効果でセットする場合も「支払わずに」表記が無ければ必須、qa-035）。
- クォーツコストは効果ではない支払いコスト（アクセル/ミラージュ等と同型）なので、BSGE01-C13 等の `神喰` 保護カウントも支払いに使える（qa-039、2026-08-10）。
- `属性値`（地火水風時空幻の7種、qa-033）は色とは別軸。host の【アーツ】解放条件を属性値合計で満たす。地の表記は2026-09-27ユーザー訂正をアプリ内QAへ反映。
- host が移動するとクォーツも追従し、`セット中` ではなくなる。
- **スロット上限は host が定義**（ENIGMA=左右3+中央1=7枚）、**同名クォーツ2枚以上セット不可**（qa-029）。
- host `ENIGMA[戦術オーブメント]` は「セット中クォーツの【クォーツ】を得て発揮」（【セット中】表記なし効果はこの host 経由のみ、qa-030）。ENIGMA へのセットは魂状態対象効果が必要。
- ENIGMA は Lv/BP 表記なし → **BP0 ではなく BP 不在**で BP 参照効果の対象にできない（qa-031）。ENIGMA の【セット条件】≠【合体条件】（qa-032）。
- 詳細は [`07_custom-orica-mechanics.md` §4](../10_rules/07_custom-orica-mechanics.md)。

### 4b. 派生メカニクスの「として扱う」裁定

- **【契約合体】**（qa-013, qa-014）: ソウルコアをトラッシュに置き手札から召喚を経ず合体させる効果。対象条件を満たしても**合体条件未達なら不可**。**【煌臨】としては扱わない**（qa-014）。※`契約煌臨`（重ねる＝煌臨派生）とは別物。
- **【コントラクトチェンジ】**（qa-038）: **【チェンジ】として扱う**。→ チェンジの一般ルール（[08b](../10_rules/08b_accel-change-zero-counter.md)）を適用してよい。
- **黒 / 七色**（qa-026〜028）: 黒は空間/時間/次元/闇モチーフの追加属性。**【装甲：∞】は黒も防ぐ**（相手フィールドの黒シンボル参照）。**六色 ≠ 七色**（相互に扱わない）が、七色は「六色以上」には含まれる。
